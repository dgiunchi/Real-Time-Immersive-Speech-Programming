## Abstract

Immersive speech programming lets people with no coding background shape behaviour inside virtual reality (VR) simply by speaking. The original *DreamCodeVR* system (Giunchi et al., 2024), built at University College London on the Ubiq social-VR platform, realises this by translating speech into C# that is **compiled and executed at runtime** inside Unity. This is expressive but unsafe — it runs effectively arbitrary, model-generated code on the host or headset with no validation gate — and although it runs on a Meta Quest 1/2 only as a manually **sideloaded 32-bit Mono build**, it **cannot be published to the Quest Store or run on Quest 3**, whose required IL2CPP/AOT ARM64 backend forbids runtime C# compilation (Unity Technologies, 2024a).

This dissertation presents **DreamCodeVR+**, which preserves the original generate-and-compile pipeline as a controlled baseline (Mode A) and replaces the *default* execution path with a **safe-by-construction** alternative. Speech is translated into a small, allow-listed *action plan* — a six-action JSON intermediate representation with hard numeric bounds — that a tiny, audited Unity executor runs **without compiling any code** (Mode C), making it Quest-compatible by construction. A new **Rust** orchestration backend joins the existing Ubiq network as a service peer and enforces a **fail-closed** validator that approves a plan only when it contains zero violations. Two further research arms enable comparison: a Rust-lexical-plus-Roslyn **validated-C#** path (Mode B) and a hardened **Docker/gVisor sandbox** for untrusted generated C# (Mode D).

The backend has been live-verified end-to-end against the real Ubiq RoomServer, a real OpenAI large-language model, a real .NET Roslyn service, and real Docker **and** gVisor containment; the Rust workspace is `unsafe`-free and panic-averse by compiler-enforced lint policy, passing 263 automated tests. The Unity client has since been verified live in **Unity 6**: both the safe action-plan executor (Mode C) and — newly — the original runtime-C# path (Mode A, now *gated by the validator*) drive scene changes from live backend messages, including model-generated C# that **compiles at runtime to build whole structures (e.g. a house) under guardrails that block malicious or over-large code** — demonstrating that the original pipeline can be made safe rather than abandoned. Two further additions complete the system: a safety-preserving **personalization (RAG)** layer that adapts the *aesthetic* of generated output to a user's taste yet remains subordinate to the validator (its retrieved context is treated as untrusted), and a live **web admin panel** that streams every pipeline stage and red-teams the guardrails on demand, making the system's safety behaviour transparent and reproducible. **On-device, live-verified:** on-device deployment has since been **demonstrated live on a physical Meta Quest** on the university network — a command spoken into the headset microphone was captured, transcribed, generated, validated, and compiled at runtime on-device — for the **Quest 1/2 32-bit Mono sideload** (Mode A); the **Quest 3 IL2CPP/Store** build remains future work. An **executed adversarial red-team** (a reproducible 1,057-vector corpus) additionally hardened the C# validator from a 15% to a **100%** attack-catch rate with **zero** loss of creative freedom, and a two-layer LLM intent screen neutralises malicious requests before any code is generated. A four-mode differential evaluation of functionality, latency, security and privacy is specified; remaining quantitative results and any human-subjects study are identified as future work pending data collection. The work argues that **bounding the output language is a stronger and more deployable safety lever than sandboxing the output** — while showing the unbounded path can itself be validator-gated when expressiveness is required. A final research thrust adds an **age-adaptive dual-plane safety coupling** — an opt-in, on-device voice *age-band* gate (child / teen / adult, never a precise age and never affect) whose detection of a minor *alone* tightens **both** the code-safety and the perceptual-safety plane, turning age inference from a surveillance signal into a protection one — supported by two reproducible, numpy-only ML models (a calibrated age-band gate and a continuous attack analyzer that red-teams that gate), with the platform Meta Quest age API kept authoritative and on-device microphone audio identified as future work.

# Chapter 1 — Introduction

## 1.1 Motivation: end-user programming in immersive VR

Virtual reality promises authoring environments in which people build and modify interactive worlds from inside them, rather than at a desktop through an engine's scripting interface. For the large population of non-programmers, the natural authoring interface is speech: *"make this cube red," "spin it slowly," "give it gravity."* Lowering the barrier to behaviour authoring is an active goal of end-user development (EUD) research for immersive systems, where tools have historically demanded C# or engine expertise and so excluded the very novices that VR's accessibility might otherwise empower (Yigitbas et al., 2022). Decades of programming-by-voice research further show that speech is a viable but error-prone modality for code entry, and that novices tend to express *intent* rather than syntax (Programming by Voice, 2023) — which makes an interface that maps spoken intent onto a small, validated behaviour vocabulary an attractive design point. Recent large language models (LLMs) make such mapping practical: they can synthesise programs and structured output from natural language, albeit with a well-documented reliability ceiling and systematic failure modes (Chen et al., 2021). Immersive speech programming therefore sits at a productive intersection of accessibility, voice interaction, and LLM-driven synthesis — but, as the next sections argue, the way that synthesis is *executed* determines whether the result is safe and deployable.

## 1.2 The original DreamCodeVR

The starting point for this work is *DreamCodeVR* (Giunchi et al., 2024), developed at University College London on top of the Ubiq social-VR platform and its Ubiq-Genie backend framework. In DreamCodeVR a user holds a controller trigger to record an utterance and points a ray at a target object; the spoken request is sent to a Node.js server that transcribes it with a faster-whisper speech-to-text (STT) service, prompts an LLM to **generate C#**, and ships that code back to Unity, where the `RoslynCSharp` library (Trivial Interactive, no date) **compiles and runs it at runtime** to mutate the scene. The result is a compelling demonstration of democratising VR behaviour design through speech-driven programming. DreamCodeVR+ preserves this artefact unchanged and treats it as the baseline against which a safer, deployable redesign is measured.

## 1.3 Problem statement

The original execution model has four concrete defects that this dissertation treats as central.

**(i) Unsafe runtime arbitrary code execution.** The system executes model-generated code, with no validation gate between generation and execution, on the user's machine or headset. Running program text derived from untrusted input is the classic code-injection / remote-code-execution pattern, granting that input the privileges of the host process (OWASP, 2021a). Because an LLM's output can be steered by a prompt-injected or simply erroneous request (OWASP, 2025; Greshake et al., 2023), the generated C# can in principle reach arbitrary file, network, and process APIs.

**(ii) Meta Quest IL2CPP/AOT incompatibility.** Quest builds use Unity's IL2CPP scripting backend, which compiles C# ahead of time (AOT) and provides **no runtime C# compiler** and no support for dynamic code generation (Unity Technologies, 2024a; 2024b). The runtime-compilation step that `RoslynCSharp` depends on therefore cannot exist on-device: the system's headline feature cannot ship on the headline platform.

**(iii) Unvalidated LLM output.** There is no schema, allow-list, or fail-closed check mediating between the model and execution; whatever the model emits is what runs.

**(iv) A dead supply-chain dependency.** The original server pins the `ubiq` package to a `gitpkg` host URL (`Server/package.json`), which — observed and dated during this project's setup — now returns `402 Payment Required`, so the server cannot be installed as published until the RoomServer is vendored manually.

## 1.4 Proposed approach

DreamCodeVR+ responds not by hardening the execution of model-generated code but by **changing what is generated**. The LLM is asked to emit a schema-bounded *action plan* — a small JSON intermediate representation (IR) whose only legal instructions are six allow-listed behaviours (`set_color`, `set_scale`, `move`, `rotate`, `spawn_primitive`, `set_physics`), each with hard numeric bounds (`MAX_ACTIONS = 16`, per-spawn `MAX_SPAWN_COUNT = 8`, cumulative `MAX_TOTAL_SPAWNED_PER_SESSION = 64`, scale 0.1–5.0, rotation ≤ 360°/s, mass 0.1–100, `MAX_PLAN_JSON_BYTES = 64 KiB`) — alongside an optional C# candidate retained purely for baseline comparison. **The action plan is the safety source of truth.** Because the IR is finite and allow-listed, unsafe operations are *unrepresentable* rather than merely filtered, echoing the constrained-generation lineage in which restricting output to a formal schema both improves reliability and guarantees structural validity (Geng et al., 2023; Poesia et al., 2022). A new **Rust** backend joins the existing Ubiq network as a service peer, validates the plan fail-closed, and a minimal, audited Unity executor runs it with **no compilation** (Mode C), so the deployable product is Quest-compatible and cannot escape its allow-list. The original generate-and-compile path is preserved as **Mode A**; two further research modes — **Mode B** (validated-C#: a tree-sitter lexical scan plus a .NET Roslyn semantic check) and **Mode D** (sandboxed-C# in a hardened Docker/gVisor container) — enable an honest comparison of safety strategies. Rust was chosen for principled reasons: well-typed safe Rust is provably free of undefined behaviour (Jung et al., 2018), and the workspace forbids `unsafe` and denies `unwrap`/`expect`/`panic` in core crates so the validator's safety invariants are compiler-enforced rather than review-dependent.

## 1.5 Research questions

- **RQ1 — Safety vs expressiveness.** Can a schema-bounded, allow-listed action-plan IR, enforced by a fail-closed validator, prevent the unsafe operations (out-of-bounds values, banned APIs, schema-bypass) that the original runtime-C# pipeline permits, and at what cost to expressiveness?
- **RQ2 — Quest-compatible alternative.** Does the action-plan execution model remove the runtime-compilation dependency that makes the original system incompatible with the Meta Quest IL2CPP/AOT backend, yielding a structurally deployable on-device path? *(On-device confirmation is itself a deliverable and remains future work; see Chapter 7.)*
- **RQ3 — Gate effectiveness against unsafe/malicious input.** How effectively do the Rust validation layers (the fail-closed action-plan validator; the lexical-plus-semantic C# gate) reject unsafe and adversarial inputs, including evasion attempts?
- **RQ4 — Latency / reliability trade-offs across modes.** Across the four execution modes, how do functionality, latency, security (rejection of malicious/unsafe inputs), privacy, and reliability compare, and what trade-offs do they expose for real-time immersive speech programming?

## 1.6 Aim and objectives

**Aim.** To design, implement, and evaluate a safe-by-construction architecture for real-time immersive speech programming in VR that preserves the expressive intent of the original DreamCodeVR while removing its runtime-arbitrary-code-execution risk and its Meta Quest incompatibility, and to compare it against the original and intermediate safety strategies.

**Objectives.**
1. **Analyse** the original DreamCodeVR system and characterise its safety, deployability, and supply-chain weaknesses from its actual source (Chapter 3).
2. **Design** an allow-listed action-plan DSL with hard bounds and a fail-closed validator as the default-safe execution model.
3. **Implement** a Rust orchestration backend that joins the existing Ubiq network as a service peer, with per-peer isolation, async timeouts, and privacy-safe telemetry.
4. **Implement** the two research arms: a lexical-plus-semantic validated-C# path and a hardened container sandbox.
5. **Provide** a drop-in Unity executor that runs validated action plans without compilation *(implemented; play-test pending)*.
6. **Verify** integration empirically against real Ubiq, real Roslyn, and real Docker/gVisor *(completed for the backend)*.
7. **Evaluate** the four modes on functionality, latency, security, and privacy *(methodology defined in Chapter 6; quantitative results identified as future work)*.
8. **Assess** ethics and privacy obligations, including a Data Protection Impact Assessment (DPIA) for any human-subjects study.

Mode A compiles validator-approved, model-generated C# at runtime to realise *open-ended* creative commands — building a house, tree, or castle from primitives — while a freeform lexical guardrail blocks malicious APIs and over-large code. This is direct evidence that the original generate-and-compile pipeline can be **retained and gated**, not merely replaced, with the user keeping full creative freedom inside safety bounds. *(Verified live in Unity 6.)*

The retrieved context is injected as clearly-labelled **untrusted data** (a prompt-injection guard) and the fail-closed validator still gates every output, so personalization cannot widen what may be generated — RAG is added *without* weakening the safety argument. *(Verified live.)*

12. **A perceptual and embodied safety layer for LLM-generated immersive content** (`code-policy`, `command-router`, and the Unity executor): a user-frame invariant (head-centred personal-space sphere and forward occlusion cone), scene-relational guards (generated-object provenance, no pose-to-behaviour feedback loop, bounded displacement, overlap/disguise checks), and temporal envelopes (a ≤3 Hz luminance cap, an anti-vection rotation clamp, per-peer rate limiting, and per-recipient routing), with a paper-cited perceptual red-team corpus. To the author's knowledge this "age-as-protection, not surveillance" inversion — one age band tightening code-safety and perceptual-safety together — is novel. *(Verified by automated Rust tests: `unknown_fails_safe_to_child`, `child_tightens_both_planes_vs_adult`, `age_minor_forces_hardened_csharp_gate`; see §7.12.)*

The band is a secondary safety net only; the platform (Meta Quest) age-group API remains the authoritative source and legal basis. *(Verified by automated tests: 17/17; calibration reproducible via `evaluate.py`; real-microphone and on-device Quest evaluation are future work — see §7.13.)*

# Chapter 2 — Background & Literature Review

This chapter situates DreamCodeVR+ within the literatures it draws on and extends. The system replaces an unsafe *speech → large language model (LLM) → runtime-compiled C#* pipeline with a schema-bounded "action plan" validated by a fail-closed Rust backend, with generated C# retained only behind research-mode gates. Accordingly, the review traverses end-user and speech-driven programming (2.1), LLM code generation and its risks (2.2), prompt injection and the standardised threat taxonomies that frame them (2.3), constrained and schema-bounded generation (2.4), immersive systems and Ubiq networking (2.5), runtime code execution in Unity (2.6), container and kernel isolation (2.7), Rust for secure systems (2.8), and privacy obligations for voice and VR (2.9). Section 2.10 states the gap and the thesis it implies: that bounding the *output language* is a stronger safety lever than sandboxing the output.

## 2.1 Speech and natural-language programming

The parent problem is end-user behaviour authoring in VR, where construction of interactive scenes has traditionally demanded C# and engine expertise, excluding non-programmers. DreamCodeVR (Giunchi et al., 2024) showed that speech-driven, LLM-mediated code generation can lower that barrier, letting a user simply speak an intent — *"make this cube red"* — and have a target object change. Adjacent end-user-development tools for VR, such as VREUD (Yigitbas et al., 2022), confirm strong demand for novice-facing authoring but achieve safety by restricting users to pre-built block or visual vocabularies rather than free-form speech, and so never generate arbitrary code. Immersive, in-headset authoring tools such as FlowMatic (Zhang and Oney, 2020) similarly broaden novice access to interactive-VR creation, but through visual, direct-manipulation programming rather than free-form speech. DreamCodeVR+ sits between these positions: it keeps DreamCodeVR's speech-first accessibility while removing its unsafe execution model.

The input modality itself motivates a particular design choice. Decades of voice-programming research show speech to be viable but error-prone for verbatim code entry, and that novices tend to describe *intent* rather than syntax (Pane, Ratanamahatana and Myers, 2001). Empirical work on vocal user interfaces for programming (Begel and Graham, 2006) and on user preferences and speaking styles in programming by voice (Nowrin and Vertanen, 2023) reinforces that systems should absorb natural, underspecified phrasing rather than demand dictated syntax. This is precisely why an LLM that maps messy spoken intent onto a small, validated action vocabulary is a better fit than one that dictates C#: the intermediate representation (IR) becomes the natural sink for ambiguous speech.

## 2.2 LLM code generation and its risks

The engine of the pipeline is an LLM that emits both a structured action plan and an optional C# candidate. Two facts about such models must be established. First, the *capability*: Codex and the HumanEval benchmark (Chen et al., 2021) demonstrated that LLMs can synthesise functioning programs from natural language. Second, the *reliability ceiling*: the same work reported only modest single-sample functional-correctness rates and systematic failure modes, a finding generalised across models and tasks by subsequent surveys (e.g. Huynh and Lin, 2025; Zhang et al., 2023). The empirical conclusion is that raw LLM output cannot be trusted unchecked. This is the quantitative backbone of DreamCodeVR+'s central design move: the system never executes the LLM's C# directly and instead treats the bounded action plan as the source of truth, validating everything downstream.

Executing program text derived from untrusted input is the classic code-injection / remote-code-execution pattern. OWASP classifies dynamic evaluation of attacker-influenced input as *Eval Injection* and *Code Injection* (OWASP, 2024), the class catalogued canonically as CWE-94 (MITRE, 2026), and the pattern grants the input the privileges of the host process. Running LLM-generated C# through Unity's runtime compiler is functionally equivalent: the "untrusted input" is the model's output plus whatever steered it. That this is not hypothetical is shown by real incidents in LLM agent frameworks built on `eval` (e.g. the unsafe-`eval` advisory in microsoft/autogen issue #4873, used here as a grey-literature illustration rather than a peer-reviewed source). DreamCodeVR+'s baseline (Mode A), which compiles and runs LLM-authored C# inside Unity, is exactly this hazard, and it is the hazard the rest of the architecture exists to neutralise.

## 2.3 Prompt injection and standardised threat taxonomies

The threat model assumes the LLM can be *steered* to emit malicious output. The OWASP Top 10 for LLM Applications (OWASP Gen AI Security Project, 2025) codifies the relevant risks: LLM01 (Prompt Injection) and LLM05 (Improper Output Handling). Greshake et al. (2023) demonstrated *indirect* prompt injection compromising real LLM-integrated applications, establishing that any LLM output flowing into a downstream executor is an attack surface — the model need not be "jailbroken" by the user directly. DreamCodeVR+'s mitigations map onto this taxonomy in a MITRE-style, control-by-control fashion: it treats LLM output as untrusted (LLM05), validates the action plan fail-closed, scans any C# candidate lexically and semantically, and fixes the `request_id` server-side so the model never owns its own identifier. The architecture is thus a direct, implementable response to the LLM05 guidance that LLM output must never be trusted as code.

## 2.4 Constrained, schema-bounded and grammar-constrained generation

This is the conceptual heart of the project. The action-plan IR (the `behaviour-dsl` crate: a `#[serde(tag="type")]`, `deny_unknown_fields` enum of six actions) is a deliberately tiny, allow-listed DSL whose schema is fixed. The relevant literature shows why this is powerful. Grammar-constrained decoding (Geng et al., 2023) and constrained semantic decoding (Poesia et al., *Synchromesh*, 2022) demonstrate that restricting generation to a formal grammar or schema both improves reliability and *guarantees* structural validity; PICARD (Scholak et al., 2021) showed the same for SQL by rejecting invalid continuations incrementally during decoding. The same principle underlies modern JSON-schema-constrained ("structured output") decoding and its benchmarking (e.g. Geng et al., 2025b; the efficiency follow-up Geng et al., 2025a).

The decisive property for safety is subtle but central to this dissertation: because the IR is finite and allow-listed, unsafe operations are *unrepresentable*, not merely *filtered*. There is no `set_color` argument that opens a socket, because the grammar admits no such instruction. The `code-policy` validator then enforces numeric and budget bounds fail-closed on top of structural validity. This reframes safety from "detect bad code after the fact" (the static-analysis and sandboxing posture of 2.6–2.7) to "make bad code inexpressible in the first place" — the move that differentiates DreamCodeVR+ from its DreamCodeVR predecessor.

## 2.5 Immersive systems and Ubiq networking

DreamCodeVR and DreamCodeVR+ are built on Ubiq (Friston et al., 2021), UCL's open social-VR networking platform, in which peers exchange messages routed by `NetworkId` through a TCP RoomServer. DreamCodeVR+ preserves the original three channels (audio input, selected object, backend output) and joins the room as an additional *service peer*, so the safety backend is a network participant rather than an in-engine module. This positioning matters for the threat model: trust boundaries are crossed on the wire, and the Ubiq frame format and join handshake had to be implemented exactly (two real protocol defects in the length field and the `Join` `args` encoding were found and fixed against the real RoomServer during this project).

## 2.6 Runtime code execution in Unity (Roslyn / IL2CPP / AOT)

This is the deployability half of the thesis and its hardest constraint. The original baseline compiles model-generated C# at runtime using a Roslyn-based Unity component. Unity's own documentation states that the IL2CPP scripting backend uses ahead-of-time (AOT) compilation and does not support runtime or dynamic code generation — `System.Reflection.Emit` is unavailable (Unity Technologies, *IL2CPP scripting restrictions*; *Introduction to IL2CPP*; *Overview of .NET in Unity*). IL2CPP is mandatory for the Meta Quest *Store* and for the 64-bit ARM64 target that Quest 3 and current Horizon OS require, so any architecture that depends on compiling C# at runtime cannot be Store-published or run on current-generation hardware — it is confined to manually sideloaded, 32-bit **Mono** builds on Quest 1/2 (where, as Chapter 3 documents from the project's own `ProjectSettings.asset`, it does run). This is a primary-sourced justification for the action-plan executor: Mode C dispatches vetted UnityEngine operations from a parsed plan with zero compilation, so it builds under IL2CPP/ARM64 and ships through the Store by construction. The Unity-side executor — and, indeed, the runtime-compile path itself, now *gated by the validator* — were both verified live in the Unity 6 editor for this dissertation (Chapter 7); only on-device deployment to a physical Quest remains argued structurally rather than demonstrated, as the author has no headset.

## 2.7 Container and kernel isolation

For studying genuinely untrusted generated C#, DreamCodeVR+ adds Mode D: a hardened container (`--network none`, read-only rootfs plus tmpfs, `--cap-drop ALL`, `--pids-limit`, memory/CPU caps, `no-new-privileges`, non-root UID, wall-clock timeout with `docker kill`), with a script for the gVisor `runsc` runtime. NIST SP 800-190 (Souppaya et al., 2017) is the authoritative baseline for container threats and countermeasures and justifies both the hardening flags and the project's honesty that a default container is a *soft* boundary. The salience of that honesty is underscored by the runc "Leaky Vessels" container-escape vulnerability, CVE-2024-21626 (MITRE, 2024), which shows that the container runtime's own trusted computing base is itself attackable. gVisor interposes an application kernel (Sentry) between the workload and host, so an attacker must break two disjoint kernels to escape (gVisor project, no date), with the performance cost quantified by Young et al. (2019) and compared across runtimes by Wang et al. (2022). This literature explains why sandboxing is positioned in this work as a *research* mode, not the default deployable path: the default (Mode C) avoids codegen entirely. In this project gVisor was verified live alongside plain Docker, but only the Docker boundary should be presented as the lower bound on isolation strength.

## 2.8 Rust for secure systems

The entire backend is Rust, with the workspace forbidding `unsafe` by lint policy, denying `unwrap`/`expect`/`panic` in core crates, holding the API key in `secrecy::SecretString`, and auditing dependencies with `cargo-deny`. The justification is formal, not promotional. RustBelt (Jung et al., 2018) gives the first machine-checked proof that well-typed *safe* Rust is free of undefined behaviour; because DreamCodeVR+ compiler-enforces `forbid(unsafe_code)`, the safe-subset guarantees RustBelt proves actually hold for this codebase — which matters because a memory-corruption bug in the validator would undermine every other layer. Honesty again requires the counterpoint: safety holds only for the safe subset, and real Rust systems carry risk through `unsafe` blocks and their dependency trees, as catalogued by an empirical study of security risks in the Rust ecosystem (Zheng et al., 2024). This is precisely the risk `cargo-deny` is deployed to mitigate, so the counterpoint is reflected in the engineering rather than waved away. The industrial weight of this argument is evidenced by Google (2024), which reports Android's share of memory-safety vulnerabilities falling from 76% to 24% over six years as new development shifted to memory-safe languages such as Rust.

## 2.9 Privacy in voice and VR, and DPIA obligations

DreamCodeVR+ processes push-to-talk audio and was built "privacy by construction": raw STT/LLM detail goes only to stderr, the wire and logs carry fixed reason codes, and the telemetry `TimingEvent` is asserted by test to contain no audio, transcript, or secret. This design is responsive to a concrete legal baseline. Under the GDPR, voice used for identification is special-category biometric data (Art. 9), high-risk processing of which triggers a mandatory Data Protection Impact Assessment (Art. 35), with privacy-by-design a standing duty (Art. 25) (European Union, 2016, Arts 9, 25, 35). The EDPB's Guidelines 02/2021 address virtual voice assistants specifically (European Data Protection Board, 2021), and academic studies map the broader voice-assistant privacy threat surface (Germanos et al., 2020). VR adds further sensitive signals, such as gaze and motion, that broaden the sensitive-data surface beyond voice alone, and recent work documents user concern toward LLM-powered conversational agents in immersive extended reality (Bozkir and Kasneci, 2025). DreamCodeVR+'s telemetry minimisation and reason-code design are concrete privacy-by-design measures that a DPIA section can map onto these obligations; honestly, however, an actual DPIA has not yet been conducted and remains a precondition for any user study.

## 2.10 Gap statement and comparison

Two literatures rarely meet at the point this project occupies. On one side sits *structured and grammar-constrained LLM generation* (2.2, 2.4), concerned with making model output valid and reliable. On the other sits *systems sandboxing* (2.6, 2.7), concerned with containing whatever a process does after it runs. DreamCodeVR+ argues that for end-user programming in a safety-sensitive, AOT-constrained immersive setting, the first lever is the stronger and more deployable one: if the output language admits only safe instructions, there is less — ideally nothing — left to sandbox, and no runtime compiler is required at all. Constrained generation moves safety *upstream* of execution and is therefore Store- and Quest-3-deployable in a way that runtime sandboxing of generated C# is not. The three strategies are compared in Table 2.1.

**Table 2.1 — Comparison of safety strategies for executing model-derived behaviour.**

| Axis | Static analysis (lexical + semantic scan of generated code) | Sandboxing (container / kernel isolation of generated code) | Constrained generation (schema-bounded action plan) |
|---|---|---|---|
| **Residual attack surface** | Moderate–high: bounded by analyser completeness; evasions and false negatives remain (e.g. the shallow Roslyn layer missed `System.Net.WebClient`, caught only by the lexical backstop) | Low but non-zero: runtime TCB itself is attackable (CVE-2024-21626); plain Docker is a *soft* boundary (NIST SP 800-190); gVisor reduces it further | Lowest: unsafe operations are *unrepresentable* in a 6-action allow-list, not merely detected after generation |
| **Quest Store / Quest-3 deployability** | Sideload-only: still implies runtime compilation of the analysed C#, which runs only under Mono on sideloaded 32-bit Quest 1/2 — not via the IL2CPP/ARM64 Store path and not on Quest 3 | Sideload-only at best: presupposes a runtime compiler/executor, so the same Mono/32-bit confinement applies; not Store- or Quest-3-deployable | Yes by construction: zero compilation, so it builds under IL2CPP/ARM64, ships through the Store, and runs on Quest 3 |
| **Latency cost** | Low–moderate: scanning adds per-request analysis (lexical fast; semantic adds a service round-trip) | Moderate–high: container spawn, compile-and-run, and isolation overhead per request | Lowest: validation is a bounded JSON parse plus arithmetic bounds checks |
| **Generality** | High: scans arbitrary C# | High: runs arbitrary code, then contains it | Low *by design*: only the six allow-listed behaviours are expressible — the deliberate expressiveness/safety trade-off |

The table makes the dissertation's positioning precise. Static analysis and sandboxing are *general but reactive* and, critically, both presuppose the very runtime-compilation step that confines the original system to sideloaded 32-bit Mono Quest 1/2 builds (not Store-distributable or Quest-3-compatible). Constrained generation sacrifices generality — only six behaviours can be expressed — to obtain the strongest residual-attack-surface guarantee, the lowest latency, and the only Store-/Quest-3-deployable execution path. DreamCodeVR+ therefore retains static analysis (Mode B) and sandboxing (Mode D) as research arms for studying generated C#, while making constrained generation (Mode C) the default. The central claim that the remainder of the dissertation defends is methodological: **for safety-sensitive immersive end-user programming, bounding the output language is a stronger and more deployable safety lever than sandboxing the output, and it can be enforced by construction.**

## 2.11 XR perceptual and embodied attacks: the second safety dimension

The threat surface in §2.2–2.3 concerns the *system*: untrusted code reaching the host's file, network, or process APIs. A distinct and, for immersive speech programming, equally important body of work concerns the *user*: how the immersive medium itself can be weaponised against the person wearing the headset. Krauß et al. (2024) catalogue dark patterns unique to extended reality and identify four amplifying properties — perception, spatiality, physical/virtual barriers, and device sensing — showing that most XR manipulations are familiar two-dimensional tactics re-expressed in three dimensions, but that embodiment, realism, and personalisation unlock new, bodily harm. Tseng et al. (2022) give a severity taxonomy of perceptual manipulations from recoverable (a stumble) to unrecoverable (injury, death), of which the *false-positive mismatch* — a plausible virtual chair, step, or floor with no real counterpart that lures the user to act and fall — is the most directly applicable here. The locomotion channel is concrete: Casey et al. (2021) demonstrate the *human joystick*, sub-perceptually translating the virtual world to walk a user into a real wall, and Ishii et al. (2016) steer a walker's direction by transforming the camera view; Pearlman (2020) frames such immersive harm as physical, not cosmetic. The deception channel spans cursorjacking transposed to VR (Su et al., 2022) and 3D object disguise, where a rendered object hides or misrepresents what is really present (Fujita et al., 2023). Crucially, Lee et al. (2021) not only demonstrate WebVR fraud but provide the defensive blueprint this dissertation adopts — *confinement* of untrusted content to what the user can legitimately see (a field-of-view/visibility constraint, forbidding behind-camera placement, and entity-rate caps) — while Valluripally et al. (2020) contribute an attack-tree-plus-statistical-model-checking method for bounding the probability that a system reaches a user-harm state.

The unifying observation is decisive for DreamCodeVR+: **the harm is compositional, relational, semantic, and temporal, not a property of any single action's magnitude.** A wall of individually in-bounds primitives still occludes; a sequence of sub-threshold moves still drifts the user; a legal colour change repeated rapidly still strobes; a correctly-scaled object placed at the head is still a projectile. The allow-list and numeric bounds of Chapters 4–5 are therefore *necessary but not sufficient*: they delete the catastrophic system-level classes — camera, locomotion, input, network — by making them unrepresentable, yet leave the perceptual/embodied classes expressible within bounds. DreamCodeVR+ answers this with a defence-in-depth ordered by strength: capability omission; a fail-closed validator; a **user-frame invariant** (an un-spoofable, head-centred personal-space sphere and forward occlusion cone that no generated object may enter or occlude); **scene-relational** checks (no pose-to-behaviour feedback loop, generated-object provenance, no false load-bearing affordance, bounded displacement); and **temporal envelopes** (a ≤3 Hz luminance-change cap following WCAG 2.3.1, an optic-flow/vection limit, and per-peer generation rate limiting). The user-frame invariant and the scene-relational layer are the novel contribution, because an invariant holds however many in-bounds actions are composed, which the per-action numeric validator cannot. These layers are implemented in the deployable Mode-C executor (`ActionPlanExecutor` / `PerceptualSafety`) and are opt-in via a comfort setting, so free creation is unconstrained while the safety demonstration arms them; Mode A is retained as the original full-freedom baseline, gated only against system access. Honest residuals, returned to in §8, remain: pose-free safety degrades when a bare headset cannot supply a trusted head pose; cumulative/composite effects require stateful temporal accounting split across backend and client; cross-peer attacks await message authentication; and false-affordance detection needs scene-semantic reasoning the action set does not represent.

All sources cited in this chapter appear in the reference list with resolvable URLs or DOIs, and none has been invented. The review establishes only the prior work against which the contribution is positioned; no empirical DreamCodeVR+ results, user studies, or Quest, speech-to-text, or large-language-model outcomes are asserted here.

# Chapter 3 — Analysis of the Original DreamCodeVR System (the Mode-A Baseline)

## 3.1 Purpose and scope

This chapter analyses the original DreamCodeVR system as it actually exists in the inherited source tree, in order to extract the concrete weaknesses that motivate the DreamCodeVR+ redesign. DreamCodeVR is a published research artefact (Giunchi *et al.*, 2024) whose central idea — letting a user shape a virtual scene by *speaking* — is preserved and built upon throughout this dissertation. The analysis below is therefore deliberately fair: the claim defended is **not** that the original "does not work", but the narrower and verifiable proposition that the original is *unsafe by default, deployable to a Meta Quest only as a sideloaded 32-bit Mono build (and therefore neither Store-distributable nor Quest-3-compatible), and — as observed during this project's setup — not installable as published because one of its dependency hosts is dead.* Each weakness is grounded in the original source files (`Unity/Assets/CodeGenerationManager.cs`, `Unity/Assets/Scenes/Scripts/TestRoslyn.cs`, `Server/samples/apps/code_runtime_generator/app.js`, `Server/package.json`) and forms the Mode-A baseline against which Modes B–D are later compared.

## 3.2 The original pipeline, traced end to end

The original system is a four-process pipeline carried over UCL's Ubiq social-VR networking layer (Friston et al., 2021). A user wearing the headset holds a controller trigger to record a push-to-talk utterance and points a selection ray at a target object. The Unity client (Unity `2021.3.16f1`; scene `Unity/Assets/Demos/DynamicCompiler/DynamicCompiler.unity`) streams the captured PCM audio to a **Node.js Ubiq-Genie server** over Ubiq `NetworkId` 98 (`NID_AUDIO_INPUT`), each body prefixed with a 36-byte ASCII peer UUID and bracketed by `__STT_CONTROL__:start` / `:stop` control frames. The server's `MessageReader` on NID 98 forwards the accumulated audio to a **Python faster-whisper speech-to-text (STT) service** (the original `README.md` points this at an HTTP endpoint, `http://130.136.2.161:50101`). The returned transcript is prepended with a `>` sentinel and passed to a **`CodeGenerationService`**, which prompts the **OpenAI API** to emit C# source. The server returns that C# to Unity over `NetworkId` 94 (`NID_BACKEND_OUTPUT`) as a JSON `{type, peer, data}` message (`app.js:111`). On the client, `CodeGenerationManager` (registered on NID 94, `CodeGenerationManager.cs:27,53`) receives the message and, with no intervening checks, hands the raw `message.data` string to `TestRoslyn` (`CodeGenerationManager.cs:87–94`), which calls `domain.CompileAndLoadMainSource(...)` (`TestRoslyn.cs:111`) — the **RoslynCSharp** asset's runtime compiler — to compile the generated C# into a fresh assembly and execute it against the selected object. Object selection itself travels separately over `NetworkId` 93 (`NID_SELECTED_OBJECT`). The headline property of this design is that *the language model's output is executed as native code on the device*, immediately and unconditionally.

## 3.3 Weakness 1 — Runtime arbitrary code execution on the host/headset

The most serious weakness is structural: the system performs the equivalent of `eval` on untrusted, model-generated input. `CodeGenerationManager.ProcessMessage` takes the C# arriving on NID 94 and passes it directly to the runtime compiler with no validation gate of any kind (`CodeGenerationManager.cs:83–96`); the compiled assembly then runs with the full privileges of the Unity process. There is no allow-list, no namespace restriction, and no human or programmatic confirmation step between generation and execution. Because the C# is whatever the LLM produced — and the LLM's behaviour is steerable through the user's spoken prompt and any upstream content — this is a textbook instance of the code-injection / arbitrary-code-execution class (OWASP, no date a; MITRE, 2026), and of OWASP's *Improper Output Handling* risk for LLM-integrated applications (OWASP Gen AI Security Project, 2025a). A generated (or prompt-injected) program could legitimately reach `System.IO`, `System.Net`, `System.Reflection`, or `System.Diagnostics` and read files, open sockets, or spawn processes, all inside the user's session. The original project's own notes acknowledge the exposure plainly, listing under risks "security (we can inject what we want in a Quest)" (`README.md`). The RoslynCSharp asset does ship an optional security-sandbox/allow-list facility, but the baseline scene does not configure it as a fail-closed gate ahead of execution; safety, where present, is opt-in rather than enforced by construction. This single property is the primary motivation for DreamCodeVR+'s thesis that *bounding what may be generated is a stronger safety lever than auditing what was generated*.

## 3.4 Weakness 2 — Confined to sideloaded 32-bit Quest builds; not Store-publishable or forward-compatible

The second weakness concerns *how* the headline feature can reach the headline device. Runtime C# compilation depends on generating and loading new managed code while the application runs, which requires a just-in-time-capable scripting backend. On Android/Quest that means Unity's **Mono** backend with a 32-bit **ARMv7** target — and the original project is configured exactly so (`Unity/ProjectSettings/ProjectSettings.asset`: `scriptingBackend{Android:0}` = Mono, `AndroidTargetArchitectures: 1` = ARMv7). Under Mono, RoslynCSharp's `ScriptDomain.CompileAndLoadMainSource` compiles and runs generated C# *on-device*, so the original system **can be sideloaded onto a Quest 1/2 and genuinely works there** — a fact corroborated by the original authors' demonstrations and not disputed here. (An earlier draft of this dissertation overstated the constraint as outright "IL2CPP/AOT non-deployability"; the precise, primary-source-grounded position is the one given here.)

The weakness is that this sideloaded-Mono envelope is the *only* one the design admits, and it is a shrinking one. First, the **Meta Quest Store** requires the **IL2CPP** backend with a 64-bit **ARM64** target; IL2CPP compiles all C# *ahead of time* (AOT) and provides no runtime C# compiler or dynamic code generation (`System.Reflection.Emit` is unsupported under AOT) (Unity Technologies, 2024a, 2024b). The runtime-compile design therefore **cannot be published through the Store** — only manually sideloaded. Second, **Quest 3 and current Horizon OS require 64-bit applications** (32-bit support is deprecated), so the Mono/ARMv7 build that makes runtime compilation possible **will not run on current-generation hardware**. Third, bundling the full Roslyn compiler into a mobile build is a heavy footprint for a wearable. The net constraint is that the original's expressiveness is purchasable only at the cost of confinement to sideloaded, 32-bit, Mono Quest 1/2 builds — unsafe (Weakness 1), undistributable through the Store, and not forward-compatible. This is a deployability constraint independent of the safety one, and it motivates a path that needs *no* runtime compilation at all (Mode C): such a path builds under IL2CPP/ARM64, ships through the Store, and runs on Quest 3. Chapter 7 reports that the runtime-compile path itself was nonetheless reproduced **and made safe** in this project — model-generated C#, validated by the Rust gate, compiled at runtime in the Unity 6 editor — confirming both that the mechanism is real and that DreamCodeVR+ can gate it rather than abandon it.

## 3.5 Weakness 3 — Missing validation gate and global `isGenerating` serialisation

The third weakness has two facets, both visible in the server's pipeline (`Server/samples/apps/code_runtime_generator/app.js`). First, there is **no validation gate** between the LLM and execution: the transcript is forwarded to code generation (`app.js:96`) and the resulting C# is relayed verbatim to the client (`app.js:111–115`), which compiles it. Nothing in the path inspects the generated code, checks it against a schema, or constrains it to a known-safe operation set — the design trusts the model's output as code. Second, the server enforces a single **global `isGenerating` flag** as its only concurrency control (`app.js:29,72,92,116`). A request is admitted only when `isGenerating == false` (`app.js:72`); the flag is then set `true` for the duration of generation (`app.js:92`) and cleared when the C# returns (`app.js:116`). This is a *global* lock, not a per-peer one: while any one user's utterance is being processed, every other user's transcript that crosses the length threshold is silently discarded rather than queued or handled on an independent session. In a multi-peer social-VR setting this both serialises throughput across all participants and fails open into dropped commands, with no feedback to the affected user. Together these two facets — no output validation and a single coarse global serialisation point — define the safety-and-concurrency gap that the DreamCodeVR+ `code-policy` validator and per-peer `command-router` sessions are designed to close.

## 3.6 Weakness 4 — A dead supply-chain dependency (observed)

The fourth weakness was discovered while attempting to stand the original server up for this project, and is reported as an *observed, dated* fact rather than a permanent property of UCL's infrastructure. The server pins its core Ubiq networking dependency to a `gitpkg` host: `"ubiq": "https://gitpkg.now.sh/UCL-VR/ubiq/Node?176b628c..."` (`Server/package.json:15`, mirrored in `Server/package-lock.json:16,1536`). During this project's setup, in June 2026, that host returned **HTTP 402 Payment Required**, so `npm install` could not resolve the dependency and the server could not be installed as published. The practical consequence is that the original artefact is not reproducible out-of-the-box from its manifest. This is consistent with established guidance on software-supply-chain fragility — pinning a runtime dependency to a third-party transformation/CDN host rather than a versioned, archived package introduces exactly this single point of failure. For this dissertation the issue was mitigated by **vendoring the real Ubiq RoomServer directly from the `UCL-VR/ubiq` GitHub repository** into a local working copy, which restored a runnable server and enabled the live verification reported in later chapters. The honest framing is that the upstream source remains available on GitHub; what is dead is the specific `gitpkg.now.sh` *fetch URL the manifest depends on*, observed on the dates recorded above.

## 3.7 Implications for the redesign

The four weaknesses are not independent annoyances but a coherent argument for a different execution model. Weaknesses 1 and 3 say the system trusts and immediately runs model-authored code with no gate; weakness 2 says the mechanism that does so cannot ship on the target device anyway; weakness 4 says the published artefact is, as observed, not even installable. DreamCodeVR+ responds by retaining the original generate-and-compile path as a controlled baseline (**Mode A**, preserved but not wired into the new Rust flow) and replacing the *default* path with a schema-bounded action plan that is validated fail-closed and executed without compilation. Table 3.1 maps each weakness to its consequence and the corresponding DreamCodeVR+ response.

**Table 3.1 — Original weakness → consequence → DreamCodeVR+ response.**

| # | Weakness in the original (Mode A) | Consequence | DreamCodeVR+ response |
|---|---|---|---|
| 1 | Runtime arbitrary code execution: LLM C# compiled and run with no validation gate (`CodeGenerationManager.cs:87–94`; `TestRoslyn.cs:111`) | Model/prompt-injected code can reach file, network, process and reflection APIs on host/headset with session privileges | Default **Mode C**: speech → allow-listed six-action plan executed by an audited Unity component that **compiles nothing**; unsafe operations are *unrepresentable*. Generated C# only reachable behind a research flag, guarded by lexical + Roslyn-semantic checks (Mode B) and a hardened sandbox (Mode D) |
| 2 | Runtime C# compilation incompatible with Quest IL2CPP/AOT (`System.Reflection.Emit` unsupported AOT) | Headline feature cannot deploy on the headline device; confined to Mono editor/desktop | **Mode C** removes the runtime-compilation dependency entirely → AOT-compatible by construction (on-device confirmation is an outstanding deliverable; see §7.7) |
| 3 | No output validation gate + single global `isGenerating` lock (`app.js:72,92,116`) | LLM output trusted as code; multi-peer commands serialised and silently dropped during any in-flight request | **`code-policy`** fail-closed validator (approve iff zero violations) + **`command-router`** per-peer sessions (`HashMap<peer, session>`, no global lock) with per-call async timeouts and a single spawn-budget chokepoint |
| 4 | Core `ubiq` dependency pinned to `gitpkg.now.sh` (`Server/package.json:15`), which returned **HTTP 402** during this project (observed, dated) | Server not installable as published; artefact not reproducible from its manifest | RoomServer **vendored from `UCL-VR/ubiq` GitHub**; `cargo-deny`/`cargo-audit` supply-chain gate on the new Rust workspace; recommendation to vendor/version-pin the RoomServer (future work) |

In summary, the original DreamCodeVR is a compelling demonstration of speech-driven behaviour authoring whose *execution model* — not its idea — is the problem. It is unsafe by default, not AOT-deployable, and (as observed during this project) not installable as published. These three precise, source-grounded findings frame the requirements and threat model developed in Chapter 4 and the safe-by-construction architecture of Chapter 5.

# Chapter 4 — Requirements, Threat Model and Design Goals

This chapter turns the weaknesses of the original DreamCodeVR baseline (Chapter 3) into an explicit specification for DreamCodeVR+. It first states the functional and non-functional requirements, then develops a threat model — assets, adversaries, attack surface and trust boundaries — and finally distils both into a small set of design goals that the architecture of Chapter 5 must satisfy. The governing principle, derived directly from the analysis, is that *the deployable system must never execute server-supplied code and must degrade to a refusal on any error*: safety is sought **by construction** and **fail-closed**, not by detection after the fact.

## 4.1 Functional requirements

The system must preserve the end-user experience of the original while changing what is generated. A user holds a controller trigger, points a ray at an object, and speaks; the scene changes accordingly. Concretely, the backend must (F1) accept push-to-talk audio and an object selection over the existing Ubiq channels and return a decision; (F2) translate a spoken request into a schema-bounded *action plan* drawn from a fixed, allow-listed instruction set; (F3) execute that plan on the Unity client **without compiling any code**, so that the default path runs on a Meta Quest; (F4) support multiple simultaneous peers, so that one user's request can never stall another's; and (F5) retain the original generate-and-compile path (Mode A) and the two C# research arms (Modes B and D) for comparison, without contaminating the default-safe path. The original Ubiq message identifiers are kept unchanged — NID 98 (audio in), NID 93 (selection in) and NID 94 (decision out) — so that the new backend is a drop-in service peer.

## 4.2 Non-functional requirements

The non-functional requirements encode the lessons of Chapter 3 and are summarised in Table 4.1. They span Quest-deployability (no runtime code generation on the default path), fail-closed safety (approve a plan only when it carries zero violations), Ubiq/NID compatibility, privacy-by-design (no transcript or audio ever persisted; only reason codes), reliability (per-peer isolation; the backend survives a sandboxed crash), and supply-chain and memory-safety hygiene (an `unsafe`-free, panic-averse workspace).

**Table 4.1 — Requirements traceability (requirement → design goal → implementing component → evidence).**

| ID | Requirement | Goal | Implemented in | Status / evidence |
|----|-------------|------|----------------|-------------------|
| NF1 | Quest-deployable default: no runtime C# compilation on Mode C | G1 | `behaviour-dsl`, Unity `SafeBehaviourRegistry` | Structural; on-device run not yet demonstrated (see §7.7) |
| NF2 | Fail-closed validation: approve iff zero violations | G2 | `code-policy::validate_plan` | Verified live (real Ubiq → `ApproveActionPlan{set_color #FF0000}`); 13 unit tests |
| NF3 | Ubiq/NID 98/93/94 compatibility preserved | G6 | `protocol`, `unity-transport` | Verified live against the real RoomServer |
| NF4 | Privacy-by-design: reason codes, never transcripts | G3 | `command-router`, `observability` | Leak test asserts no audio/transcript/secret field can appear |
| NF5 | No global lock; concurrent peers isolated | G2 | `command-router` per-peer `HashMap` | Verified live (per-utterance tasks) |
| NF6 | `unsafe`-free, panic-averse; clean supply chain | G4, G5 | workspace lints, `cargo-deny`/`audit` | `unsafe_code = forbid`; gate green (263 tests) |
| NF7 | Bounded resource use (plan size, spawn budget) | G2 | `bounds.rs`, `code-policy`, `commit` | `MAX_PLAN_JSON_BYTES=64 KiB`; cumulative 64-spawn cap |

## 4.3 Assets, adversaries and trust boundaries

**Assets.** Three assets must be protected. (A1) the **host and headset** — the Quest device and the host machine must never run attacker-controlled native code or reach the file, network or process APIs. (A2) the **backend process** — it must stay available, and one peer must not be able to deny service to others. (A3) the **user and their data** — voice and transcripts are minimised and never logged; their integrity and confidentiality must hold.

**Adversaries.** Following the OWASP Top 10 for LLM Applications (OWASP, 2025), the model is treated as untrusted output, not trusted logic. Three adversaries are in scope: (1) a **careless LLM** that, without malice, emits invalid, out-of-bounds or unsafe output (the empirical reliability ceiling of code-generating models (Chen et al., 2021)); (2) an **adversarial prompt or indirect injection** — a user, or content the model ingests, that steers it toward unsafe output, the indirect-injection class demonstrated against real LLM-integrated applications (Greshake et al., 2023) and codified as OWASP LLM01 (Prompt Injection); and (3) a **malicious generated payload** — generated C# that, if compiled and run, would attempt arbitrary file, network or process access (OWASP code-injection class; CWE-94), the precise hazard of the Mode A baseline.

**Attack surface and trust boundaries.** The wire surface is the three Ubiq channels. Untrusted bytes arrive on NID 98 and NID 93 from *any* room peer; decisions leave on NID 94. Three trust boundaries follow: **TB1 untrusted → backend** (bytes on NID 98/93); **TB2 LLM output → execution** (all generated text and code is untrusted at this crossing); and **TB3 backend → Unity** (NID 94, where the client executes *only* allow-listed actions and never compiles server-supplied C#). The peer identifier on NID 98/93 is self-asserted, so peer authenticity is *not* assumed inside a connection — an explicitly accepted risk (§4.5).

**Table 4.2 — Threat model: asset · adversary · attack surface · mitigation · status.**

| # | Asset | Adversary | Surface / boundary | Mitigation | Status |
|---|-------|-----------|--------------------|-----------|--------|
| T1 | Host/headset (A1) | Malicious payload | TB3 NID 94 | Action-plan execution only; no compilation on Mode C; client re-clamps bounds | Backend verified; Unity play-mode VERIFIED live in Unity 6 (Mode C + validator-gated Mode A) |
| T2 | Host/headset (A1) | Malicious C# (Mode B) | TB2 LLM→exec | Defence-in-depth: tree-sitter lexical scan **+** .NET Roslyn semantic check, both fail-closed | Verified live; honest finding: Roslyn missed `System.Net.WebClient` (false negative), Rust lexical layer is the backstop and rejects `System.Net` |
| T3 | Host/headset (A1) | Untrusted C# under study (Mode D) | TB2 LLM→exec | Hardened container: `--network none`, read-only rootfs + tmpfs, `--cap-drop ALL`, pid/mem/cpu limits, `no-new-privileges`, non-root, wall-clock timeout + `docker kill`; only a report crosses back | Verified live under **both** Docker and gVisor (`runsc`) |

## 4.4 Design goals

Six design goals (G1–G6) discharge the requirements and threats above.

**G1 — Safety by construction (bounded action DSL).** The default path bounds *what the model may generate* rather than scanning free-form output afterwards. The action plan is a six-variant, internally-tagged, `deny_unknown_fields` JSON intermediate representation whose enum **is** the allow-list (`set_color`, `set_scale`, `move`, `rotate`, `spawn_primitive`, `set_physics`), each with hard numeric bounds in a single source of truth (`MAX_ACTIONS=16`, per-spawn `MAX_SPAWN_COUNT=8`, scale 0.1–5.0, rotate ≤360°/s, mass 0.1–100). Unsafe operations are *unrepresentable*, not merely filtered — the schema-constrained-generation lineage (Geng et al., 2023; Poesia et al., 2022) made operational. This directly removes the Quest-blocking runtime-compilation dependency, since the client only dispatches vetted UnityEngine operations.

**G2 — Fail-closed everywhere.** The validator approves a plan *iff* the violation set is empty; oversized input is rejected *before* parsing (anti-allocation DoS); and every external call (STT, LLM, Roslyn) is wrapped in a timeout that degrades to a refusal. A cumulative spawn budget is enforced at a single chokepoint (`commit`), which downgrades an otherwise-valid plan to a rejection once the per-session cap of 64 is reached.

**G3 — Defence-in-depth for the research C# path.** Because Modes B and D exist to *study* generated C#, the false-negative observed in the shallow Roslyn semantic layer (it references only corelib and missed `System.Net.WebClient`) is treated as expected, not as a single point of failure. Safety on this path is the *combination* of four layers — lexical scan, semantic check, plan↔C# consistency, and sandbox — consistent with NIST SP 800-190's position that a container alone is not the security claim (NIST, 2017). The lexical layer runs first and rejects `System.Net` syntactically, so it is the verified backstop for what the semantic layer misses.

**G4 — No global lock; privacy-safe telemetry.** Per-peer sessions in a `HashMap` (no `isGenerating`-style global serialisation) give concurrency isolation, and telemetry records only ids, timestamps, decisions, reason codes and counts — never transcripts — so that a leak is structurally impossible rather than merely avoided.

**G5/G6 — Minimal CVE surface and preserve Mode A.** The workspace is `unsafe`-free and panic-averse by compiler-enforced lint, with `cargo-deny`/`cargo-audit` gating the supply chain; and the original Roslyn baseline is preserved unchanged for honest comparison, kept off the default path behind a research flag.

## 4.5 Accepted and deferred risks

Three risks are accepted and stated plainly, not hidden. The wire `peer_uuid` is **self-asserted**: connection-level isolation holds, but within one connection a client could touch another peer's session bookkeeping; per-message authentication is deferred. Per-peer rate-limiting and an anti-strobe min-plan-interval are now enforced in `command-router`, and the Unity Mode-C client auto-reconnects after a dropped link. And **kernel-level isolation**, while verified under gVisor in the laboratory, is not the default Mode-D runtime in the Rust runner. The Unity client's play-mode behaviour has since been **verified live in Unity 6** (Mode C and validator-gated Mode A drive object changes from live backend messages); what remains is the four drop-in headless EditMode tests under a licensed batch Editor, and on-device Quest hardware.

# Chapter 5 — Architecture & Implementation

This chapter describes the DreamCodeVR+ system as it was actually built. The guiding design principle is that *safety is layered and centralised*: there is one place that defines what the system may do (the action-plan allow-list), one place that decides whether a request is safe (the fail-closed validator), one place that enforces cumulative resource limits (the spawn-budget chokepoint), and one place that maps internal errors onto wire-visible reason codes (the privacy boundary). Generated C# — the original system's only execution path — is demoted to a research arm reachable only behind a flag, and even then only through lexical, semantic, and sandbox layers in series. The emphasis throughout is on these design decisions and the trade-offs behind them rather than on the code itself.

## 5.1 Workspace shape and the four modes

DreamCodeVR+ is a Cargo workspace of twelve library crates and four binary applications, with a separate cross-crate test crate, living entirely in a `dreamcodevr-plus/` directory placed *beside* the unchanged original Unity/C# project. This side-by-side layout was a deliberate decision: the original DreamCodeVR pipeline is preserved as the Mode A baseline, while every new component is isolated, so the dissertation can compare against the original without modifying it.

The library crates contain pure logic with no binaries; the binaries (`dreamcodevr-server`, `fake-quest-client`, `ubiq-probe`, `sandbox-runner`) are thin shells over them. Two further .NET microservices (a Roslyn analyser and a sandbox worker) sit outside the Rust build because they require the .NET toolchain, and a set of drop-in Unity C# scripts replace the original runtime-compile manager on the client side.

The system realises four execution modes. Mode A is the preserved original (LLM → C# → `RoslynCSharp` compiled inside Unity); it is kept as a research control and is *not* wired into the Rust flow. Mode B is a Rust-validated C# path. Mode C — the deployable default — executes a schema-bounded action plan with *no compilation*, making it Quest-compatible. Mode D isolates untrusted C# in a hardened container. The defining decision is that the language model is asked to emit *both* a structured `action_plan` and a `csharp_candidate`, but the action plan is the single safety source of truth.

## 5.2 The networking layer

Unity and the backend communicate over Ubiq (UCL's social-VR networking library), in which a TCP RoomServer relays messages between peers addressed by `NetworkId`. Three channels are reused unchanged from the original system: NID 98 carries push-to-talk audio (or, in the mock path, UTF-8 transcript text) from Unity to the backend; NID 93 carries the selected object (`"objectName:materialName"`); and NID 94 carries the backend's decision back to Unity.

The `protocol` crate is a pure codec — no I/O, no async, and `unsafe` forbidden. The wire frame is `[u32 LE body_len][u32 LE a][u32 LE b][payload]`, where the critical detail is that `body_len = 8 + payload.len`: the length prefix counts the eight-byte `NetworkId` *plus* the payload, not the payload alone. Both `encode_frame` and `decode_frame` reject payloads above 1 MiB before allocating, and `decode_frame` never panics, returning an `Incomplete { needed, have }` signal so a partial stream can be resynchronised. A *golden test* pins the exact bytes for NID 98 carrying `"AB"` (`0A000000 00000000 62000000 4142`), locking the encoding against silent regression. A small payload helper handles the 36-byte ASCII peer-UUID that Unity prefixes onto NID 98/93 bodies.

The `unity-transport` crate is the async Ubiq peer. `UbiqServicePeer::connect_and_join` opens the TCP socket, sends a Join control frame to the RoomServer's reserved `NetworkId(0,1)`, waits for a `SetRoom` reply, then spawns reader, writer, and one-second ping tasks. It exposes a cloneable `PeerSender` so that work spawned off the receive loop can still emit frames.

Two real protocol bugs were found here only through live testing against the genuine RoomServer (vendored from `UCL-VR/ubiq` because the upstream `gitpkg` host now returns 402). The first is the `body_len` semantics above, confirmed against the real source and now pinned by the golden test. The second is subtler: the Join message's `args` field must be a *stringified* JSON value, not a nested object, because the Node RoomServer executes `JSON.parse(message.object.args)`. A nested object failed schema validation with "is not of a type(s) string"; this was the bug actually blocking the real-Ubiq join, and without live testing it would have surfaced only when wiring Unity. Both are recorded honestly as discoveries of empirical, not unit, testing.

## 5.3 The action-plan IR

The `behaviour-dsl` crate is the heart of the safety argument: it defines the action-plan intermediate representation as pure serde data. An `ActionPlan` carries a schema version, a request id, a target, and a list of actions, and is annotated `#[serde(deny_unknown_fields)]`. The `Action` type is an internally tagged enum (`#[serde(tag = "type")]`) with exactly six variants — `set_color`, `set_scale`, `move`, `rotate`, `spawn_primitive`, `set_physics`. The decisive design choice is that *this enum is the allow-list*. There is no catch-all variant, so any unknown `type`, or any extra top-level field, is rejected at parse time. Unsafe operations are therefore not filtered after the fact; they are simply *unrepresentable* in the IR.

A single `bounds.rs` module is the one source of truth for every numeric limit: at most sixteen actions per plan, at most eight spawned objects per `spawn_primitive`, a cumulative sixty-four spawns per session, scale within 0.1–5.0, speed and amplitude at most 5, rotation at most 360°/s, mass within 0.1–100, a 64 KiB plan size cap, and a hex-colour validator. Centralising these means the validator, the orchestrator, and the documentation all read the same constants rather than duplicating magic numbers.

Because the Unity executor must re-clamp to the same limits, those constants are mirrored by hand into `ProtocolModels.cs`. Hand-mirroring is a drift risk, so it is guarded by an automated `bounds_parity` test in the cross-crate test crate that fails `cargo test` if the Rust and Unity constants diverge — turning a documentation-discipline problem into a compiler-enforced one.

## 5.4 The fail-closed validator

The `code-policy` crate is the gate. `validate_json` rejects any input larger than the 64 KiB cap *before parsing*, an anti-allocation defence so that an attacker cannot force a large parse simply by sending a large body. It then parses and calls `validate_plan`, which accumulates a `Vec<ValidationError>` covering the schema version, empty or oversized action lists, every per-action numeric range (with an explicit `NonFiniteValue` guard rejecting NaN and infinities, which would otherwise slip past naïve range checks), and the spawn budget. The defining rule is *approve iff zero violations*: the validator returns `ApproveActionPlan` only when the violation set is empty, and `RejectUnsafe` otherwise. Fail-closed is thus the structural default — any error, any unrecognised field, any out-of-range value collapses to rejection.

## 5.5 Orchestration

The `command-router` crate owns a `HashMap<peer_id, PeerSession>` with *no global lock*. This is a direct response to a weakness of the original system, whose global `isGenerating`-style serialisation meant one user's request blocked another's; here, per-peer sessions guarantee one peer can never stall another. The router exposes three pipelines: a synchronous `process_transcript` for the deterministic mock path; an async `process_audio` that runs STT → LLM → validate, each external call wrapped in a `tokio::time::timeout`; and `process_audio_dual`, the Mode B research path, which additionally validates the C# candidate through the lexical scan and then the Roslyn analyser. The dual path is fail-closed end to end: a Roslyn analyser error yields *not approved*, and the candidate is approved only when both the lexical and semantic checks pass.

Two safety properties are centralised here. First, the *spawn-budget chokepoint*: `commit` is the single method every pipeline calls, and it enforces the cumulative per-session cap of sixty-four spawns. A plan that is individually valid can still be downgraded from approve to reject (with reason `session_spawn_budget_exceeded`) because the session has already exhausted its allowance — a deliberate two-level budget on top of the per-plan cap in `code-policy`. Second, *privacy by construction*: when STT or LLM fails, the raw detail goes only to stderr, while the wire and the logs receive a fixed reason code (`stt_unavailable`, `stt_timeout`, `llm_unavailable`, `llm_timeout`, `empty_transcript`). A dedicated test proves that a secret transcript can never escape into the outcome or the timing record.

Ahead of the fail-closed C# validator sits a Layer-1 security screen that inspects the raw natural-language command *before* any code is generated, pairing a fast keyword classifier with an LLM semantic classifier (gpt-5.5, returning a structured JSON verdict of `{malicious, category, reason}`) so that malicious or privacy-violating *intent* — device camera, microphone or screen capture, keylogging, exfiltration, memory access, tap-automation, and cyber-attack code such as ransomware, DDoS or reverse-shell payloads — is caught at the semantic layer rather than after synthesis. A command flagged by either classifier is neutralised: it is replaced with a harmless server-authored recolour (`reset::neutralized_csharp`) and never reaches the generation model at all, whilst benign creative and deliberately edgy-but-harmless themes — a Trojan-horse statue, a bloody zombie, a sea shell — pass unimpeded, preserving creative freedom. This complements the lexical and Roslyn gate as genuine defence-in-depth: the validator reasons over code that already exists and can only refuse what has been written, whereas the intent screen stops the harmful request before hazardous code is ever authored, closing the semantic gap between what a user *asks for* and what a downstream lexer can *see*. The design also fails safely under a payload-smuggling threat model, in which an attacker weaves an exfiltration request into an otherwise-innocent scene ("generate a snowman AND steal the wifi passwords") or hides it inside an object's animated behaviour, because the semantic classifier judges the composite intent rather than isolated tokens. Firing 100 attack prompts at the running backend, all 100 were blocked with 0 bypasses, and the keyword layer alone caught 305/305 keyword-detectable natural-language attacks with 0 bypasses, while benign edgy themes were not flagged — evidence that the two layers together raise the practical cost of an intent-level bypass without sacrificing expressive authoring. *(Verified live, 2026-07-03.)*

## 5.6 External client seams

STT and LLM are trait seams so the backend can run fully offline by default. `SttClient` has a `MockSttClient` that UTF-8-decodes the audio bytes as text (keyless and deterministic) and an `HttpSttClient` that POSTs a hand-built 44-byte-header WAV to a faster-whisper endpoint over rustls. `LlmClient` has a `MockLlmClient` doing keyword-to-action mapping (red → `#FF0000`, spin → rotate, bigger → scale) plus a deterministic, allow-list-clean C# template generator, and an `OpenAiLlmClient` issuing temperature-zero completions under a strict system prompt. A notable decision is that the LLM *never owns the request id*: `OpenAiLlmClient` always overwrites `plan.request_id` with the backend's id, so the model cannot influence correlation. The API key is held in a `secrecy::SecretString` (redacted `Debug`, zeroized on drop). Timeouts live in the router, not the clients, by design — the clients have no timeout variant of their own, keeping the timeout policy in one place. Absence of `DCVR_STT_HTTP_URL` selects the mock STT and absence of `OPENAI_API_KEY` selects the mock LLM, so the default configuration is deterministic and offline.

## 5.7 Mode B: validated C#

Mode B treats generated C# as a research arm guarded by defence-in-depth. The `csharp-policy` crate is the first layer: `validate_csharp` uses a tree-sitter C# parser to scan for banned namespaces (`System.IO`, `System.Net`, `System.Reflection`, `System.Diagnostics`, `System.Threading`, `System.Runtime.InteropServices`, and `Application.Quit`) and banned identifiers (`SendMessage`, `Destroy`, `PlayerPrefs`, reflection verbs, `InvokeRepeating`). Matching is by dotted-name reconstruction, so whitespace, `global::`, `@`-escapes, and comment tricks cannot evade it; the layer also enforces a length cap and requires exactly one top-level MonoBehaviour. A `consistency_check` cross-validates the C# against the plan (for example, that spawn counts agree). A dedicated red-team test suite exercises evasion attempts.

The `roslyn-client` crate is the second layer, a `RoslynAnalyzer` trait whose `HttpRoslynAnalyzer` POSTs the candidate to the .NET service and is fail-closed (`unwrap_or(false)` — a missing field, a non-2xx response, or any error means *not approved*); the `MockRoslynAnalyzer` approves by default so the backend runs without a .NET toolchain. The .NET service itself parses with Roslyn, builds a semantic model, and rejects symbols resolving into the six denied namespaces.

An honest finding from live testing shapes how this is presented. The semantic analyser references only corelib, so symbols outside corelib resolve to null and are silently skipped — `new System.Net.WebClient` was returned as approved (a false negative), because `System.Net.Requests` is not corelib. A strict allow-list was tried first but false-rejected the generated class's own `<global namespace>`, so the service was changed to deny-list only. This is why C# safety is explicitly *not* this service alone: in the real dual path the Rust lexical layer runs *first* and rejects `System.Net` purely syntactically, so the candidate never reaches Roslyn. The episode concretely demonstrates why the C# story is defence-in-depth (lexical backstop + semantic check + consistency + sandbox), not a single gate.

An executed adversarial red-team against the tree-sitter lexical scanner exposed three evasion classes that a naïve subsequence ban over identifier segments cannot see. The first was namespace-aliasing: a declaration such as `using Sys = System;` followed by `Sys.IO.File.WriteAllText(...)` reconstructs as the segment list `[Sys, IO, File]`, which never contains the banned `[System, IO]` subsequence, smuggling file IO, sockets and threading past the lexer while the leaf identifiers remain individually innocuous. The second was Unicode-escape identifiers — C# decodes `\uXXXX` within an identifier, so `Application.\u0051uit()` presents an AST leaf of `\u0051uit` (which is not `Quit`) yet compiles to the real `Quit`. The third was dynamic late-binding, where `((dynamic)app).Quit()` reaches a banned member through a node that carries no banned identifier at all. Each was closed at source in `crates/csharp-policy/src/lexical.rs`: a using-alias pre-pass builds an alias-to-target map and expands a leading alias segment — transitively, to cover chained aliases — before the subsequence check; a decoding step normalises `\uXXXX`/`\UXXXXXXXX` in identifier text prior to matching; and the `dynamic` keyword, which has no legitimate use in a generated MonoBehaviour, is banned outright. Re-firing the identical 727-vector corpus, attack-catch rose from 39/258 (15.1%) to 258/258 (100%) with zero bypasses, while all 469 benign "creative-freedom" vectors — including a cube named `TrojanHorse` and a minimap `Camera` — remained approved, preserving a 0% over-block rate. The result is locked by five new regression tests, with the `csharp-policy` crate passing 15 unit tests and the full corpus firing in roughly one second of pure lexical analysis *(Verified live, 2026-07-03.)*

## 5.8 Mode D: the sandbox

Mode D exists to study genuinely untrusted generated C#. The `sandbox` crate defines a `SandboxRunner` trait whose `run` returns a structured `SandboxReport` — the *only* thing that crosses back; no live process handle escapes. The `DockerSandboxRunner` runs each job in a container hardened with `--network none`, `--read-only` plus a tmpfs `/tmp`, `--cap-drop ALL`, a pids limit, memory and CPU caps, `no-new-privileges`, and `--user 65534:65534`. The untrusted code is streamed to the container's stdin, and on timeout the runner issues `docker kill` so the daemon (not the CLI) tears the container down; argument construction is unit-tested without Docker. A `SandboxWorker` adds retry and a dead-letter queue, with a non-zero program exit treated as a *report*, not a retried failure. The .NET harness behind it reads C# from stdin, compiles it in-memory with Roslyn referencing all runtime assemblies (so it works offline under `--network none`), runs the entry point, and returns stdout/stderr with a structured exit code. The honest framing is that Docker alone is a deliberately *soft* boundary per NIST SP 800-190 (NIST, 2017); kernel-level isolation via gVisor is the stronger option.

## 5.9 The Unity drop-in

On the client side, five drop-in scripts replace the original `CodeGenerationManager`. `ActionPlanNetworkBridge` registers on `NetworkId(94)`, receives the decision JSON, and invokes the executor — and must be the *only* component registered on NID 94, replacing the original runtime-compile manager. `ActionPlanExecutor` parses the envelope with Newtonsoft, fail-safes on bad input, and dispatches each action to `SafeBehaviourRegistry`, the client-side allow-list that maps each action to exactly one vetted UnityEngine operation with re-clamped bounds and no reflection, I/O, networking, or compilation. `ProtocolModels` mirrors the Rust bounds (guarded by the parity test of §5.3) and `GeneratedObjectTracker` enforces the sixty-four-object cap with an `UndoAll`. Four NUnit EditMode tests accompany these, but they run only inside Unity.

## 5.10 Quality gates

Finally, safety properties are mechanically enforced rather than left to review. The workspace lint policy makes every crate opt into `unsafe_code = "forbid"` and denies the clippy `unwrap_used`, `expect_used`, and `panic` lints, so the entire backend is `unsafe`-free and panic-averse by compilation. A `check.sh` gate runs `cargo fmt --check`, `clippy --all-targets -D warnings`, the test suite, and a release build, and `deny.toml` enforces supply-chain hygiene. The gate is green: formatting, clippy, 263 tests, release build, and `cargo-deny` all pass.

## 5.11 Verification status

To be explicit about scope, the components above differ in how far they are proven. The backend's real-Ubiq roundtrip, Mode B (including the `System.Net` false negative and the Rust lexical backstop), and Mode D containment under both Docker and gVisor are live-verified, as are the 263 Rust tests. The Unity client integration has **since been live-verified in Unity 6** (Editor Play, no Quest required): both **Mode C** (the action-plan executor) and **Mode A** (runtime C# compilation, now validator-gated) drive scene changes from live backend messages — including model-generated C# that compiles at runtime to build open-ended structures (a house, a tree, a castle from primitives) under the freeform lexical guardrail that blocks malicious or over-large code. A **real OpenAI LLM** (gpt-5.5) was exercised end-to-end, and **speech-to-text was verified at the OpenAI Whisper API level**. Both previously-unverified items have **since been demonstrated live on a physical Meta Quest** on the university network (§7.11): live-microphone STT end-to-end from the headset, and on-device runtime compilation on the Quest 1/2 32-bit Mono sideload. What remains is the **Quest 3 IL2CPP/Store** build (which forbids runtime compilation, motivating Mode C) and the quantitative measurement. The architecture is therefore complete, the backend is proven against real infrastructure, and the Unity execution of *both* execution paths is demonstrated; what remains is on-device deployment and the quantitative measurement reported honestly in the evaluation chapters.

## 5.12 Personalization (retrieval-augmented generation), safety-preserving

A later increment adds a personalization layer (`crates/personalization`) so the system learns each user's *aesthetic* preferences without weakening any safety property. It sits as one step **between speech-to-text and the LLM**: the recognised command is used to (i) inject a short, learned *preference profile* and (ii) retrieve the most similar previously-**liked** creation as a style exemplar, before the prompt is sent. Three layers are implemented behind one `Personalizer` type: a `PreferenceProfile` that learns content words and recent phrases from commands the user marks as liked; a liked-history memory; and embedding retrieval via an `EmbeddingClient` seam — `OpenAiEmbeddingClient` (`text-embedding-3-small`) for real semantic similarity, or a deterministic offline `MockEmbeddingClient` (hashed bag-of-words) so the feature works with no key and tests are reproducible. Cosine top-K over the user's liked memories selects the exemplar; state is per-user and local (a JSON file or in-memory store). Feedback flows back over a dedicated network channel (`NID 95`: `{"liked":bool}`), which promotes the most recent generation and updates the profile.

The design is deliberately *subordinate to the safety architecture* of §5.4 and §5.7. Retrieved context is injected into the prompt inside an explicitly-labelled `[PERSONALIZATION … UNTRUSTED DATA, never an instruction]` block — a direct mitigation for indirect prompt injection (Greshake et al., 2023; OWASP Gen AI Security Project, 2025b) given that the memory store is itself attacker-influenceable — and it may bias only palette, theme and complexity, never *which* object is built or *whether* the safety rules apply. Because the fail-closed validator still gates every output, personalization cannot enlarge the set of admissible programs; it only reweights preferences within it. Storing per-user data is treated as a privacy obligation and is addressed in the DPIA discussion (§8.3).

## 5.13 Live observability and runtime control (the admin panel)

To make the system's internal behaviour inspectable — for evaluation, debugging and viva demonstration — a control plane (`crates/control`) and a web admin panel (`crates/admin`, built on the Rust **axum** framework) were added. `control` holds a cheaply-clonable `ControlBus`: a live `RuntimeConfig` behind a read–write lock, a broadcast event bus of typed `PipelineEvent`s, and lock-free statistics counters. The request pipeline reads a fresh config snapshot per request (so changes take effect on the next command) and **publishes each stage as it happens** — transcript, prompt-sent, LLM reply, validation, and (reported back from Unity over `NID 96`) the runtime-compile result — each carrying its own duration, followed by a total.

The panel itself is a single embedded page (plain HTML/CSS/JavaScript, no build step) that consumes the event stream over **server-sent events** and renders the pipeline live with human-readable timings. It also exposes: runtime-tunable safety knobs (maximum generated-C# size and line count, per-mode enable/disable, model selection, RAG depth) applied through the same `ControlBus`; lifetime statistics including approval/rejection counts, malicious-blocked count, and an indicative token-cost estimate; a safety log of every rejected or neutralised command; a paste-a-snippet validator that runs arbitrary C# through the real guardrail; a **red-team runner** that fires a fixed set of malicious samples and confirms each is blocked (with a benign control that must pass); per-user RAG profile inspection; and a manual command box that drives the real pipeline. Mutating routes are guarded by an optional admin token. Architecturally the panel is a *window into the running backend* — it shares the same `ControlBus` and validator rather than re-implementing them — so what it displays is exactly what the pipeline does. This converts otherwise-opaque safety behaviour into reproducible, demonstrable evidence, and is used as such in Chapter 7.

Three refinements were made to the admin panel to close the gap between observation and control. First, the manual-command box no longer merely validates: it now shares the live Ubiq sender and, on approval, emits an NID-94 `{type,peer,data}` message so that a typed command is compiled and built in the connected headset exactly as a spoken one would be – giving a reliable, speech-free means of driving a demonstration. Secondly, the runtime-config POST was changed from a full-body replacement to a partial merge, overlaying only the altered field onto the current configuration, so that the panel's Apply now takes effect live rather than failing on a partial body. Thirdly, the headline "malicious blocked" KPI was corrected so that a Layer-1 neutralisation increments this counter directly – and is excluded from the "approved" tally – ensuring the figure reflects the true number of interventions instead of reading zero while catches accrued silently under a separate metric. Together these changes make the panel an instrument of runtime control as well as of observation, without compromising the safety pipeline. *(Verified live, 2026-07-03.)*

# Chapter 6 — Evaluation Methodology

This chapter specifies *how* each claim in this dissertation was or would be evaluated, *before* any results are reported. It is deliberately separated from Chapter 7 so that the evaluation design can be judged on its own merits, independently of the data it produced. The chapter follows a design-science logic (analyse the original artefact, build an alternative, evaluate it differentially) and is explicit about the boundary between what was executed against real infrastructure, what was exercised only by automated tests with in-process mocks, and what is *planned but not yet run*. No quantitative result is anticipated here; that honesty is the point.

## 6.1 Evaluation design

The central design is a **differential, four-mode comparison**. The same speech-derived prompts are driven through four execution paths — Mode A (original runtime-compiled C# baseline), Mode B (Rust-lexical + Roslyn-validated C#), Mode C (schema-bounded action plan, the deployable default), and Mode D (isolated Docker/gVisor sandbox) — so that any difference in functionality, latency, security or privacy can be attributed to the *execution architecture* rather than to the input. This isolates the effect of the project's core claim, that bounding the output language (Mode C) is a stronger and more deployable safety lever than sandboxing or scanning free-form code (Modes B and D).

The design distinguishes three evidentiary tiers, which are carried through into Chapter 7 unchanged:

- **Live-verified** — exercised against real external infrastructure (the real Ubiq Node RoomServer, a real .NET 10 Roslyn service, real Docker, and real gVisor `runsc`).
- **Automated-test-only** — exercised by the Rust test suite against in-process or local mock servers (not the real OpenAI/faster-whisper/RoomServer services).
- **Planned, not yet run** — specified here but blocked on hardware, credentials, or a sign-in step (Unity play-mode; real STT/LLM; on-device Quest; a possible human-subjects study).

## 6.2 How each claim was evaluated

**Unit and integration tests.** The functional and safety logic of the backend was evaluated by the workspace test suite — **263 Rust tests** run under a mechanically enforced gate (`cargo fmt --check`, `clippy --all-targets -D warnings`, `cargo test`, `cargo build --release`, `cargo-deny`, `cargo-audit`). These cover the fail-closed validator (approve-iff-zero-violations), the per-peer session model, the spawn-budget chokepoint, and the privacy reason-code mapping. One test is load-bearing as an *evaluation instrument* in its own right: the **bounds-parity drift guard** (`tests/tests/bounds_parity.rs`), which fails the build if the hand-mirrored Unity `ProtocolModels.cs` constants and NIDs diverge from the Rust `behaviour-dsl/bounds.rs` source of truth. This converts an otherwise silent manual-sync hazard into a checked invariant.

**Live Ubiq round-trip (Mode C path).** The single largest integration risk — that the Rust backend can actually join and converse on UCL's Ubiq network — was evaluated empirically, not assumed. The real Node RoomServer was run, and `ubiq-probe` plus the full `dreamcodevr-server` + `fake-quest-client --ubiq` loop were driven through it, with the end-to-end success criterion being a NID-94 reply received back through the real server.

**Mode B (validated C#).** Evaluated by live `curl` against the running .NET Roslyn service (`:5099`) over a small adversarial input set, *and* by the dual-path run through real Ubiq with `DCVR_CSHARP_RESEARCH=true`. The two-layer design (Rust lexical scan first, Roslyn semantic check second, fail-closed on either) was specifically probed to test whether a weakness in one layer is caught by the other.

**Red-team C# corpus.** The lexical scanner (`crates/csharp-policy`) was evaluated against a dedicated evasion suite (`redteam_tests.rs`) probing whitespace, `global::`, `@`-prefix and comment tricks against the banned-namespace and banned-identifier lists, plus plan↔C# consistency fixtures in `fixtures/csharp/`.

**Mode D containment.** Evaluated by running deliberately hostile payloads — write-to-rootfs, network exfiltration, runaway loop, and `File.WriteAllText("/etc/pwned")` — inside the hardened runner under **both** plain Docker and gVisor (`runsc`). The success criterion is that each payload is *contained* (blocked or killed) and that only a structured report crosses back, with the backend surviving every case.

## 6.3 Metrics

For claims that are qualitative today, the metrics are defined here so the gap is measurable later:

- **Functional success rate** per mode: fraction of corpus prompts that produce the intended scene change.
- **Per-stage latency** (STT, LLM, validation, total), reported as **p50/p95/p99** computed from the privacy-safe JSONL `TimingEvent` stream, which already records the necessary ids/timestamps/counts (and, by test-asserted construction, *no* audio or transcript).
- **Security rejection rate** on a red-team set: fraction of malicious prompts / unsafe C# / schema-bypass / NID-spoofing attempts correctly rejected (fail-closed) — and, conversely, false-rejection rate on benign inputs. The red-teaming methodology follows established practice in adversarially probing language models for harmful outputs (Ganguli et al., 2022; Perez et al., 2022).
- **Containment rate** for Mode D: fraction of escape attempts blocked.
- **Reliability**: backend survival under concurrent peers and under sandbox crashes.

## 6.4 Planned but not-yet-run evaluations

The following are designed but were **not executed**, and are reported as such throughout:

- **Unity Editor EditMode tests (Mode C logic proof).** Four NUnit tests (`AcceptsSetColor`→red, `ClampsOversizeScaleDefensively`, `RejectsInvalidJson`, `RejectsEmptyActions`) are staged into `Unity/Assets/DreamCodeVRPlus/`. They are **blocked on Unity sign-in** in *headless batchmode*: it quit at the licensing stage (`Access token is unavailable`) before compilation, so this is an account step the automation cannot perform — not a code fault. The *interactive* Unity 6 Editor play-mode (both Mode C and validator-gated Mode A) has since been verified live (§7.5); only this headless EditMode batch run remains pending.
- **Real STT/LLM latency.** The faster-whisper and OpenAI code paths exist but default to deterministic mocks; no real endpoint/key was measured.
- **Differential A/B/C/D latency.** Requires the real endpoints above (and, for Mode A, wiring the preserved baseline into the flow), so the latency CDFs are not yet collected.
- **A possible human-subjects study.** An optional, adults-only red-team exercise is envisaged but is **conditional on University of Birmingham ethics approval and a completed DPIA**; none has been sought.

## 6.5 Threats to validity

The design's honesty depends on naming its limits. **LLM nondeterminism** is controlled by defaulting to deterministic mock clients and, for any real run, fixing temperature to 0 over N repetitions — but generality across providers is not established (**single-provider** threat). **Construct validity:** a qualitative "it round-tripped" is not a measured success *rate*, and Chapter 7 does not present it as one. **Internal validity:** the `fake-quest-client` is not Unity, so the round-trip evidences the backend and protocol, not the Unity executor. **External validity:** the simulator/desktop environment is **not a Quest device**, so on-device latency and FPS remain unmeasured; and **Docker is a deliberately soft boundary** (NIST SP 800-190) — the stronger kernel-isolation claim rests on the gVisor run, which used CLI-level `timeout` rather than the production Rust `docker kill`. The **Roslyn semantic layer is deny-list-only and shallow**, so its rejection rate must always be reported as one layer of defence-in-depth, never as a standalone gate. These threats bound every result in Chapter 7.

## 7.2 Live Ubiq round-trip (Mode C path) — verified

The full speech-to-behaviour loop was exercised through the **real** Ubiq RoomServer with no Unity involved. `ubiq-probe` joined and reported `JOINED OK. Listening for NID 98 / NID 93.`; the RoomServer log confirmed both peers joining and leaving the room. The `fake-quest-client --ubiq` peer sent a NID-93 selection plus NID-98 push-to-talk (`start` / "make this cube red" / `stop`), and received back through the real server:

```
NID 94: {"decision":"ApproveActionPlan", action: set_color "#FF0000"}
```

The server's JSONL telemetry recorded `decision=ApproveActionPlan, action_count=1, errors=[]` — confirming, as a side-result, that no transcript leaked into the log. Two real protocol bugs were found and fixed *by this live test* (not by unit tests): the Ubiq frame length counts `NetworkId(8) + payload`, not payload alone; and the `Join` message's `args` must be a **stringified JSON** because the server does `JSON.parse(message.object.args)` (`roomserver.js:401`). This is the qualitative success criterion of RQ2's deployability path; it is **not** a measured success rate, and is not reported as one.

## 7.3 Mode B (validated C#) — verified, with a defence-in-depth finding

The .NET Roslyn service was exercised live (`curl /analyze`). The observed results, including one deliberately surfaced false negative, were:

| Input | Roslyn result |
|---|---|
| clean MonoBehaviour | `approved:true` |
| syntax error | `approved:false` ("syntax errors") |
| `System.IO.File.ReadAllText` | `approved:false` ("denied namespace: System.IO") |
| `System.Reflection.Assembly…` | `approved:false` ("denied namespace: System.Reflection") |
| **`new System.Net.WebClient`** | **`approved:true` ← FALSE NEGATIVE** |

The honest finding: the semantic analyzer references only corelib, so `System.Net.WebClient` (in `System.Net.Requests`, not corelib) fails to resolve and is silently skipped — the documented *shallow* nature of the deny-list-only semantic layer. **The Rust lexical layer is the backstop and does catch it**: `dcvr-csharp-policy` rejects `System.Net` purely syntactically (`redteam_tests.rs:68` rejects `new System.Net.Http.HttpClient`; `csharp_tests.rs:58` asserts `BannedToken("System.Net")`). In the real Mode-B dual path the lexical scan runs *first*, so `System.Net` is rejected before Roslyn is consulted. This is a concrete demonstration of *why* C# safety must be defence-in-depth (lexical + semantic + consistency + sandbox) and why the Roslyn service alone is not a sandbox. The clean template C# passed *both* layers end-to-end through real Ubiq, returning NID-94 `csharp_decision:"ApproveCSharpResearchMode"`.

## 7.4 Mode D containment — verified under Docker AND gVisor

Containment was verified under **both** plain Docker and the gVisor (`runsc`) userspace kernel. Under Docker, shell payloads in `alpine` and real generated C# in the `.NET` Roslyn harness (`dcvr-sandbox-harness:local`) were both contained. Under gVisor, the benign container reported kernel **`4.19.0-gvisor`** — proving syscalls are intercepted by the application kernel rather than reaching the host — and the same payload classes were contained. The combined observed results:

| Scenario | Docker | gVisor (`runsc`) |
|---|---|---|
| benign | `Completed 0`, `uid=65534` | `OK uid=65534 kernel=4.19.0-gvisor` |
| write rootfs | `READONLY_BLOCKED` | `READONLY_BLOCKED` |
| network exfil | `NETWORK_BLOCKED` | `NETWORK_BLOCKED` |
| runaway / infinite loop | `TimedOut` → `docker kill` | killed by wall-clock, host unaffected |
| real C# benign | `Completed 0` ("hello from sandboxed C#", ~1.7 s) | ran → "hello from gVisor-sandboxed C#" |
| real C# runtime exception | `Completed 70` (caught) | — |
| `File.WriteAllText("/etc/pwned")` | `FS_BLOCKED: IOException` | (read-only rootfs) |

In every case the backend process survived and all `--rm` containers were auto-reaped. One honesty caveat carried from Chapter 6: the gVisor runaway-kill here was driven by CLI-level `timeout`, whereas production uses the Rust `DockerSandboxRunner`'s `docker kill`; running the *Rust* runner under gVisor requires adding `--runtime=runsc` to `build_args`.

## 7.5 Unity 6 execution — Mode C and Mode A verified live (no Quest)

Both client execution paths were verified live in **Unity 6 (6000.5.1f1)**, in Editor Play mode, with no Quest hardware. A self-contained Ubiq TCP client joins the same room as the Rust backend (avoiding any external Ubiq-package version risk) and applies the backend's NID-94 messages to a target object.

**Mode C (default, no compilation).** With the backend in its default action-plan mode, commands round-trip end to end: the object's colour, scale, and motion change from the backend's validated action plan, executed by the audited `SafeBehaviourRegistry` with zero runtime compilation. This confirms the Quest-compatibility argument empirically on the client side.

**Mode A (original runtime-C#, now validator-gated).** With the backend set to `DCVR_MODE_A=true`, the system reproduces the *original DreamCodeVR pipeline* on modern Unity: a command is sent to the LLM, which returns a C# `MonoBehaviour`; the **Rust gate validates it**; only if it passes is it sent on NID 94 as `{type:"code", data}`; and a self-contained Roslyn component (`RuntimeCSharpCompiler`) **compiles it at runtime in the editor (Mono JIT) and attaches it to the object**. A command such as *"make it spin and turn purple"* produces, within a few seconds, a freshly-compiled behaviour running on the cube — the first end-to-end demonstration in this project that the original generate-and-compile loop works *and* is gated by the safety validator. Because the editor uses the Mono backend this needs no Quest; the same build would run sideloaded on a Quest 1/2 (§3.4) but is out of scope without hardware.

**Open-ended creative generation under guardrails.** Mode A is *not* limited to the six action-plan verbs. Because the C# path is gated by the **freeform** validator — a lexical/structural security scan (banned namespaces and reflection/process/IO verbs, `unsafe`, exactly one `MonoBehaviour` class, a size cap) rather than a plan-consistency check — the user has full creative freedom. Commands such as *"make a small house"*, *"make a tree"*, *"make a castle"*, *"build stairs"* and *"make a snowman"* generate multi-primitive C# that constructs the structure from `GameObject.CreatePrimitive` parts parented to the target, and compiles and runs live. In a sample of such commands generated with gpt-5.5, **5/5 were approved by the guardrail and built the requested structure**; the same guardrail **rejects** code that reaches a banned capability (`System.IO`, `System.Net`, reflection, `Process`, `Resources`, …) or exceeds the size bound — freedom is bounded by *security and resource* limits, not by expressiveness. This realises the dissertation's "made safe, not removed" position for the original pipeline. *Honest limitation:* the lexical guardrail does not detect a deliberately-constructed infinite loop in otherwise-clean C#; Mode D's sandbox remains the backstop for genuinely untrusted code, and Mode A presumes a cooperative-but-fallible generator gated by the validator.

**Latency.** End-to-end Mode-A latency is dominated by the LLM: simple recolour/spin commands return in roughly 3–8 s with gpt-5.5, while elaborate creative builds (a detailed house or castle) take ~15–25 s, reflecting the larger generated program; the validator and runtime compile add negligible time. A faster tier (e.g. gpt-4.1-nano) roughly halves simple-command latency at some cost to behavioural richness — a configurable per-deployment trade-off.

## 7.8 Analysis

The verified results substantiate the architectural claims qualitatively: the deployable Mode-C path round-trips through the real Ubiq protocol and returns a correctly validated action plan with no runtime compilation, executed live in Unity 6, which is the structural basis of the Quest-deployability argument (RQ2). The Mode-B finding is the chapter's most instructive negative result — a real false negative in the semantic layer that nonetheless *strengthens* the thesis, because the lexical backstop demonstrates the value of layering rather than relying on any single gate (RQ1, RQ4). Mode D's containment under both Docker and gVisor confirms that even the research arm that *does* run untrusted C# fails safe. The Unity 6 result adds a second substantive finding: the **original runtime-C# pipeline (Mode A) was reproduced and made safe** — model-generated C# is validator-gated, then compiled at runtime to realise open-ended creative commands (a house, a tree, a castle) while the freeform guardrail blocks malicious or over-large code. This shows the dissertation's safety lever is not only "replace compilation with an action plan" but, more generally, **move safety to the gate**: when full expressiveness is wanted, the generated code can be admitted *iff* it clears the security/resource guardrail (RQ1, RQ4). What the verified results do **not** yet show is any *measured* trade-off: the latency, success-rate and rejection-rate comparisons that would directly answer RQ3 and the quantitative half of RQ4 await systematic data collection, and on-device Quest hardware and live-microphone STT have since been exercised live on a physical Quest 1/2 Mono sideload (§7.11), leaving the Quest 3 IL2CPP/Store build and the quantitative measurement as the outstanding items — not any code defect. The defensible summary is that the **design is complete and both the backend and the Unity client (both modes) are proven against real infrastructure; what remains is on-device deployment and measurement, not redesign.**

## 7.9 Coverage of the XR threat literature (implemented vs outstanding)

The perceptual/embodied literature of §2.11 doubles as a coverage checklist. Each source's core attack is mapped to the DreamCodeVR+ defence and its status. *By construction* = the attack is unrepresentable in the deployable Mode-C action set; *implemented* = an explicit guard rejects, bounds or discloses it; *partial* = the direct mechanism is covered but a compositional or semantic variant is not; *future* = designed but not built.

Because the deployed configuration is **Mode B (Rust-validated full-freedom C#) + Mode D (sandbox)** rather than the six-verb Mode-C executor, the perceptual guarantees are provided in four freedom-preserving ways, none of which restricts creation by default: (i) an **opt-in C# validator profile** (`HardeningProfile::DeployHardened`) that, on top of the always-on system-access bans, also bans the *unambiguous device/rig/haptics/capture* APIs that have no content-authoring use (`OVRManager`, `XRSettings`, `InputTracking`, `OVRHaptics`, `WebCamTexture`, `UnityEngine.XR`, …), while the default `CreativeFreedom` profile keeps full expressiveness; (ii) a **runtime user-frame guardian** (`UserFrameGuardian`) that re-asserts the tracking-owned head/rig pose each frame and re-shows any hidden *registered authentic* object, enforcing the invariants a lexer cannot; (iii) **mode-agnostic monitors** (`GeneratedContentMonitor`, `UserDisplacementTracker`, `AuthenticObjectRegistry`) that *disclose* — never block — personal-space, FOV, confinement, drift and disguise concerns; and (iv) **Mode-D containment**. An adversarial verification (one skeptic per paper plus a freedom critic) drove an important correction: a lexical denylist is the *wrong* tool for the camera-transform/viewport/post-process/scene-query/object-hide vectors because the same token (`Camera.main.transform`, `RenderTexture`, `FindObjectsOfType`) is an attack on the live rig but legitimate authoring on a build's own objects — the denylist both missed the bare-transform attack and over-blocked creative builds. Those vectors are therefore enforced at *runtime* (where the live rig and authentic objects are identifiable) rather than lexically. The freedom contract — every creative build, including a preview camera, a post-effect and a recolour-all command, passes under both profiles — is test-enforced (`tests/tests/mode_b_d_defense.rs`).

## 7.10 Adversarial red-team of the C# validator and the intent screen (RQ3) — verified

RQ3 asks whether the safety layer can withstand deliberate adversarial pressure rather than merely well-formed input. To answer it empirically we built a reproducible red-team corpus generator (`redteam/corpus_gen.py`) that emits 1,057 unique attack and control vectors with no randomness, so the entire campaign is deterministically repeatable: 727 C# vectors fired at the tree-sitter lexical validator (`POST /api/validate`) and 330 natural-language vectors fired at the intent screen and generation path (`POST /api/command`) *(Verified by automated tests.)*. The 727 C# vectors comprise 258 malicious "should-block" cases and 469 benign "creative-freedom" cases, the latter deliberately including scary-looking-but-safe authoring — a cube named `TrojanHorse`, a sphere named `seashell`, and a minimap `Camera` — to probe over-blocking as well as under-blocking *(Verified by automated tests.)*. The runner (`redteam/run_campaign.py`) scores each vector against ground truth and records two failure modes: a *bypass* (a should-block vector that is approved — a critical security failure) and an *over-block* (a benign vector that is blocked — a false positive that harms creative freedom) *(Verified by automated tests.)*.

The BEFORE result is reported here as a genuine finding rather than a formality: against the unhardened validator the lexical layer caught only 39 of 258 attacks (15.1%), leaving 219 bypasses, while over-blocking 0 of 469 benign vectors (full creative-freedom pass) *(Verified by automated tests.)*. The validator was therefore near-perfect on precision but badly deficient on recall — a result that would have been invisible without the adversarial corpus.

The 219 bypasses resolved into three novel evasion classes that the subsequence-matching lexer had not anticipated:

| Evasion class | Count | Mechanism |
|---|---|---|
| Namespace alias | 204 | `using Sys = System;` then `Sys.IO.File.WriteAllText(...)` reconstructs as segments `[Sys, IO, File]`, so the banned `[System, IO]` subsequence never appears, while the leaf identifiers (`IO`, `File`, `Net`, `Threading`) are not individually banned — smuggling file IO, sockets, threading and `WebClient`. |
| Unicode-escape identifier | 10 | C# decodes `\uXXXX` inside identifiers, but the AST leaf text is the raw escape, so `Application.\u0051uit()` reads as `\u0051uit` ≠ `Quit` while the compiler resolves the real `Quit` (likewise `\u0050layerPrefs`, `\u0047etType`). |
| Dynamic late-binding | 6 | `((dynamic)app).Quit()` reaches a banned member with no banned identifier node present for the lexer to see. |

Three fixes were applied to `crates/csharp-policy/src/lexical.rs`. First, a using-alias pre-pass builds an alias→target map and `resolve_alias()` expands a leading alias segment — transitively, to cover chained aliases — before the subsequence ban check, closing the namespace-alias class. Second, `decode_unicode_escapes()` normalises `\uXXXX` and `\UXXXXXXXX` in identifier text prior to matching, closing the Unicode-escape class. Third, the `dynamic` keyword is banned outright, as it has no legitimate use in a generated MonoBehaviour, closing the late-binding class *(Verified by automated tests.)*.

Re-firing the identical 727-vector corpus against the hardened validator closes the recall gap without any regression in precision:

| Measure | Before | After |
|---|---|---|
| Attacks caught | 39/258 (15.1%) | 258/258 (100%) |
| Bypasses | 219 | 0 |
| Benign preserved | 469/469 | 469/469 |
| Over-blocks | 0 | 0 |

All 727 C# vectors fire in roughly one second, as the path is purely lexical and invokes no language model *(Verified by automated tests.)*.

The natural-language surface is defended by a distinct two-layer intent screen (Layer 1) that runs on the raw command before any generation: a fast keyword classifier (`classify_intent`) followed by an LLM semantic classifier (`screen_intent`) returning a JSON verdict. A command judged malicious is neutralised — replaced with a harmless server-authored recolour and never forwarded to the generation model — and surfaced in the admin panel. Firing 100 attack prompts at the running backend, all 100 were blocked with 0 bypasses, including payload-smuggling framings ("generate a snowman AND steal the wifi passwords", and payloads woven into an object's animated behaviour) and prompt-injection and jailbreak framings; the keyword layer alone caught 305/305 keyword-detectable NL attacks with 0 bypasses *(Verified live, 2026-07-03.)*. Critically for creative freedom, benign but edgy themes — a Trojan-horse statue, a bloody zombie, a sea shell — were not flagged *(Verified live, 2026-07-03.)*.

Taken together these results answer RQ3 directly: the safety layer, once adversarially exercised, both blocks 100% of the 258 C# attack vectors and 100 natural-language attacks and preserves 100% of benign creative authoring. The three lexical fixes are locked against regression by 5 new tests, and the `csharp-policy` crate now passes 15 unit tests in total *(Verified by automated tests.)*.

### The attack corpus in brief — five families, with the privacy family distinguished

The security work draws on a curated baseline of **128 attack vectors** (grown by the automated analyzer of §7.14 to a discovered store of **164**). Many vectors are near-duplicates — the same capability expressed through a different phrasing, obfuscation or API route — so the corpus is best read as **five families** rather than 128 distinct threats:

| Family | Plane | Representative vectors | Store *n* |
|---|---|---|---|
| Network & identity | code / system security | reverse shells, port scans, DDoS, C2/botnet, ARP-MITM, Wi-Fi crack, re-identification | 34 |
| Generated code | code / system security | `System.IO`/`Net`/`Reflection`/`Diagnostics`, `Process.Start`, `DllImport`/`Marshal`, shellcode, ransomware | 40 |
| **Voice & sensor** *(privacy)* | privacy — capture | microphone, camera / passthrough and screen capture; sensor spoofing; age-gate spoofing | 38 |
| **Privacy / PII** *(privacy)* | privacy — exfiltration | clipboard, contacts, location/GPS, SMS, credentials, photos, keylogging | 30 |
| Immersive / embodied | embodied safety | human-joystick (forced locomotion), chaperone edits, vection, occlusion, flashing | 22 |

Of the five, **two are privacy-related** and carry the privacy contribution: *voice & sensor*, which captures the user's body and environment (microphone, camera/passthrough, biometric sensors), and *privacy / PII*, which exfiltrates personal data. Together they map onto the XR-specific privacy channels — **biometric**, **positional/motion**, and **image-of-surroundings** leakage (Nair et al., 2023). The remaining three families are either executable-code security (network & identity, generated code) or embodied-safety **manipulation** (immersive: the human-joystick and chaperone attacks of Casey et al., 2021, which are safety rather than privacy harms). Because the vectors within a family are largely obfuscation or phrasing variants of one another, the argument is carried by the families, not the individual strings; the full per-vector listing is deferred to Appendix C.

To quantify the defence against these classes without a headset, a dedicated local harness (`apps/xr-security-eval`) runs each attack through the real validator at three levels — no defence, security-only, and fully hardened. The result is a clean before/after: **100%** of attacks succeed with no defence, **95%** are blocked once the backend is fully hardened, and **all** benign creative commands still pass. A finding that motivates the layered design emerges directly: a code-security filter alone stops privacy *exfiltration* (which uses system/network APIs) but misses pure XR *manipulation* — the human-joystick class stays at 100% and chaperone at 88% under security-only — so only the perceptual/embodied layer catches those. Two subtle joystick vectors that abuse otherwise-legitimate camera moves remain a documented residual for runtime enforcement.

## 7.11 On-device Quest deployment on the university network — verified live

The system was exercised end-to-end from a physical Meta Quest headset connected to the backend over the university lab Wi-Fi. The device under test was a Quest 1/2 running the 32-bit Mono sideload (package `com.DefaultCompany.ubiqgenie`), which executes the Mode-A runtime-compilation path — generated C# is compiled on the headset at runtime via RoslynCSharp. Because the installed application dials a server IP baked in at build time (192.168.8.213), and DHCP had since reassigned the laptop to 192.168.8.210, connectivity was restored without rebuilding the app by making the laptop reachable at the baked address — a secondary IP alias was added with `ip addr add 192.168.8.213/24 dev wlo1`. The headset then established a TCP connection to the Ubiq RoomServer, observed as `192.168.8.202 -> 192.168.8.213:8009 ESTABLISHED` *(Verified live, 2026-07-03.)*.

With the room joined, the full live-microphone speech-to-text pipeline was driven from the physical headset. A command spoken into the Quest mic — "generate me planet Jupiter and all its moons" — was streamed over Ubiq (NID 98), transcribed by OpenAI Whisper, generated by gpt-5.5, validated by the C# policy layer, and dispatched back to the headset (NID 94) for runtime Roslyn compilation and instantiation in the scene. Simple commands complete generation in approximately 20 seconds *(Verified live, 2026-07-03.)*. The same dispatch channel was confirmed from the admin panel's manual-command box: a typed instruction is validated and then sent to the headset over the shared Ubiq sender, so a manually authored command also builds in VR rather than merely validating *(Verified live, 2026-07-03.)*.

A latent failure was discovered and fixed during this live session. The reasoning model had been configured at "high" effort with an 8000-token completion ceiling; on the Jupiter command it spent essentially its entire budget on hidden reasoning tokens and returned empty visible content. Downstream this parsed as an end-of-file condition, was mapped to `llm_unavailable`, and caused the command to be wrongly rejected. The default was changed to "medium" reasoning effort with a 24000-token ceiling, after which generation succeeded and the objects were produced *(Verified live, 2026-07-03.)*.

The scope of this result should be stated honestly. What has been verified on-device is the Quest 1/2, 32-bit Mono sideload running the Mode-A runtime-compilation path — a locally provisioned, IP-addressable deployment on the university network. The Quest 3 IL2CPP build and a Meta Store distribution path remain future work and are not claimed here; Mode A's runtime C# compilation is specific to the Mono sideload and does not transfer unchanged to an IL2CPP/ahead-of-time target, which would require the alternative execution strategy discussed in the future-work chapter *(Future work.)*.

## 7.12 Age-adaptive dual-plane safety coupling — verified (test)

The machine-learning thrust is reported here in three subsections (§7.12–7.14), each in the same four-part arc: **the problem**, **why we deal with it**, **what we built**, and **an honest read on whether it is enough**. The novel core of the thrust is a single coupling that lets one age signal condition *both* safety planes at once.

**The problem.** Every safety mechanism built up to this point — the fail-closed action-plan validator (§5.4), the C# hardening profiles (§7.9), and the perceptual/embodied envelopes of §2.11 — treats all users identically. But the person in the headset may be a child, and the harms are not the same. A child is more vulnerable to photosensitive flashing, to disorienting optic-flow (vection), and to being lured toward a false floor or a false chair; and, legally, a child cannot have code executed or data captured on the strength of their own consent. A single global safety setting is therefore pitched wrongly for someone: loose enough for an adult is too loose for a child, and tight enough for a child needlessly constrains an adult. Concretely, neither the code-safety plane nor the perceptual-safety plane was conditioned on *who* the user is.

**Why we deal with it.** Age matters here for bodily and legal reasons, not abstract ones. The amended COPPA rule (16 CFR 312, 2025) now treats biometric identifiers as covered personal information and takes effect in April 2026; GDPR Art. 8 and the UK Age-Appropriate Design Code (ICO Children's Code) impose a duty of care toward minors; and the immersive harms of §2.11 fall harder on children. The move we think is genuinely novel — and ethically the right way round — is to use an age signal for *protection, not surveillance*: a detected minor makes the system safer and does nothing else (no profiling, no precise age retained, no other downstream use). To stay clear of the EU AI Act (Art. 5, in force February 2025), which restricts emotion recognition in many contexts, the signal is deliberately a coarse age *band* only and never an affect read.

**What we built.** A small, auditable coupling in `crates/config/src/age.rs` defines an `AgeBand { Child, Teen, Adult, Unknown }` whose default is `Unknown`, and a `for_band` mapping from band to an `AgeSafetyPosture` that spans both planes. A detected minor — or `Unknown`, which fails safe to *child* — tightens the code-safety plane (the C# validator flips to its hardened `DeployHardened` profile, and a runtime compile requires explicit confirmation) and *simultaneously* tightens the perceptual plane: relative to the Adult posture, the Child/Unknown posture turns perceptual hardening on, drops the per-command spawn budget from 40 to 20, the flash cap from 3.0 to 2.0 Hz, the field-of-view coverage limit from 0.70 to 0.35, the comfort rotation clamp from 90 to 30°/s, and the luminance-swing limit from 1.0 to 0.4. The coupling is enforced in the orchestrator (`command-router`) so that a detected minor *alone* flips the C# gate to hardened. Crucially the whole feature is opt-in behind the `DCVR_AGE_GATING` environment flag; with it off, the pipeline is *byte-identical* to the legacy path, so the coupling adds safety without changing default behaviour. Three Rust tests pin the behaviour — `unknown_fails_safe_to_child`, `child_tightens_both_planes_vs_adult`, and (in `command-router`) `age_minor_forces_hardened_csharp_gate` — and run inside the workspace's 263-test gate. Two literature anchors, *not* our own measurements, frame why a voice age band is even feasible: child-versus-adult voice is separable at roughly 97.14% age-group accuracy on CMU Kids, and motion-based age inference has been reported at about 78% per-user (Nair, arXiv:2305.19198) — the latter underscoring how much *is* inferable from a headset, which is precisely why we restrict our own signal to a coarse band.

**Is it enough? — honest evaluation.** *Proven:* the coupling logic is verified by the three named Rust tests — a minor tightens both planes, an unknown band fails safe to child, and a detected minor alone forces the hardened C# gate — and the opt-in flag is shown to leave the legacy path byte-identical when off. *Limitation:* the coupling is only as trustworthy as the age signal that drives it, and that signal (§7.13) is a coarse band that our own analyzer shows to be spoofable (§7.14); the coupling therefore *restricts* but must never be relied on to *authorise*. The specific bound values (20 spawns, 2.0 Hz, 0.35 FOV, and so on) are engineering choices informed by WCAG-style thresholds, not the outcome of a human-factors study. *Pending:* the platform age-group signal (the Meta Quest age API, 2024) remains the authoritative source and the ML band is a secondary net; an end-to-end on-device run of the coupling with real microphone audio on a physical Quest is future work (hardware available from 2026-07-23).

## 7.13 On-device voice age-band gate — verified (test)

**The problem.** To condition safety on age (§7.12) we need an age signal that runs *on the device*, cannot itself become a privacy liability, and does not overreach into a precise age or an emotional read. An off-device age service, a precise-age estimate, or an affect classifier would each create the very surveillance harm we are trying to avoid — and the harm would be pointed at children. The FTC (March 2024) has explicitly *denied* facial age estimation as a lawful COPPA consent mechanism, so an age estimate cannot be the legal basis for anything on its own; it can only make the system more cautious.

**Why we deal with it.** A protective age signal is worth building only if it is built the careful way: local, coarse, and modest about what it claims. Emitting a *band* (child <13 / teen 13–17 / adult 18+) rather than a number keeps the model within the age-assurance-level framing of ISO/IEC 27566-1:2025 and IEEE 2089.1-2024 (both standards/literature anchors), and deliberately excludes affect so the EU AI Act Art. 5 emotion-recognition concern does not arise. Keeping the model numpy-only and CPU-only makes it reproducible and auditable — a reviewer can rerun it — which matters more for a safety net than raw accuracy.

**What we built.** `ml/age_gate` is a numpy-only (no torch, no scikit-learn), CPU-only, reproducible classifier that emits a coarse band and *never* a precise age and *never* affect. It is temperature-scaled for calibration (T ≈ 1.93), which reduces validation Expected Calibration Error from ~0.05 to ~0.007, reproducible via the live `evaluate.py` (the README quotes ~0.01 and the plan document ~0.012; the reproducible live figure is ~0.007). The suite is 17/17 tests green. Two literature anchors bound expectations without being claimed as our own results: child-versus-adult voice is separable at about 97.14% age-group accuracy on CMU Kids, and edge age models have been reported at roughly 20 ms latency — both *literature anchors*, and the 20 ms figure in particular has **not** yet been measured on a Quest. A deeper wav2vec2 feature front-end is documented as an upgrade path (`wav2vec2_features.py`) but is not the evaluated model.

**Is it enough? — honest evaluation.** *Proven:* 17/17 tests pass and the calibration improvement (~0.05 → ~0.007 ECE) is reproducible from `evaluate.py`. *Limitation:* the gate is evaluated on held-out/synthetic audio, not real push-to-talk microphone capture; its features are simple by design (the wav2vec2 upgrade is written up but not run); and, most importantly, the band is *spoofable* — our own red-team (§7.14) pushes a child sample across the adult boundary 100% of the time. *Pending:* real-microphone audio and an on-device Quest run (hardware from 2026-07-23). The honest posture is the one baked into §7.12: the platform (Meta Quest) age-group API is authoritative, and this model is a secondary safety net that can only *tighten*, never authorise.

## 7.14 Continuous ML attack analyzer — verified (test)

**The problem.** A validator hardened once can quietly rot: attackers find new phrasings, the input distribution drifts, and a fixed test corpus notices neither. And the age gate of §7.13, being an ML model, must be assumed spoofable until something actually tries to spoof it. We wanted a component that watches the pipeline continuously — flagging anomalous inputs, noticing distribution shift, and actively red-teaming our own age gate — rather than trusting a one-time hardening pass to hold.

**Why we deal with it.** This closes the loop on the dissertation's safety argument: the C# red-team of §7.10 was a one-shot campaign, whereas an operational system needs *continuous* assurance, and any ML safety signal (the age band) needs an adversary of its own. Building the analyzer numpy-only keeps it auditable and CPU-only, consistent with the rest of the ML thrust.

**What we built.** `ml/attack_analyzer` combines three numpy-only pieces. An anomaly detector — a PCA/SVD undercomplete autoencoder — scores inputs by reconstruction error, achieving a pooled AUC of 1.00 with a benign false-positive rate of ~2% at a 99th-percentile threshold and per-attack-family detection of 1.0. A drift detector (ADWIN2) raised 0 false alarms on a stationary stream and detected an injected distribution shift at t = 304. And a red-team loop turns the analyzer on our *own* age gate, discovering a 100% spoof rate (a child sample pushed across the adult boundary) — a deliberately surfaced negative result. The attack corpus starts from a curated baseline of 128 vectors, and the discovered-vector store (`attacks_discovered.jsonl`) grows to 164 entries. The suite is 21/21 tests green.

**Is it enough? — honest evaluation.** *Proven:* 21/21 tests pass; the anomaly detector separates the corpus (pooled AUC 1.00, ~2% benign FPR, per-family 1.0) and the drift detector both stays quiet on stationary data and catches the injected shift at t = 304. *Limitation:* a pooled AUC of 1.00 is a property of a *controlled* corpus with clean separation, not a field claim — it says the detector cleanly handles the vectors we generated, not that real adversarial traffic will separate as neatly; and the analyzer's most useful output is arguably its honest negative, the 100% spoofability of our own age gate, which is exactly why §7.12 keeps the platform age API authoritative. *Pending:* a live-traffic evaluation against real STT/LLM endpoints and on-device capture. As with the rest of the thrust, the models are numpy-only by design — reproducible and auditable rather than maximally accurate.

# Chapter 8 — Discussion, Limitations, Ethics & Privacy

## 8.1 Interpreting the central thesis

The animating argument of this dissertation is that, for real-time immersive speech programming on a Meta Quest, *bounding the output language is a stronger and more deployable safety lever than sandboxing the output*. The verified evidence supports this claim at the architectural and integration level. The deployable path (Mode C) never compiles or executes model-authored code: the language model targets a finite, six-action, internally-tagged, `deny_unknown_fields` intermediate representation (`behaviour-dsl`), and the fail-closed validator (`code-policy`) approves a plan only when its violation set is empty. Because the action set is an allow-list enum with hard numeric bounds, an entire class of unsafe operations — banned-API access, out-of-range scaling, schema-bypass — is not merely filtered after generation but is *unrepresentable* in the first place. This is the qualitative difference between making bad code inexpressible (Mode C) and detecting or containing it after the fact (Modes B and D), and it is what makes Mode C deployable on the IL2CPP/AOT backend where runtime C# compilation is structurally impossible (Unity Technologies, 2024).

The contrast with the sandbox arm is instructive precisely because the sandbox was verified to work. Mode D was demonstrated to contain untrusted generated C# under *both* plain Docker and gVisor (`runsc`): filesystem writes (`File.WriteAllText("/etc/pwned")`) returned `FS_BLOCKED`, network access returned `NETWORK_BLOCKED`, and runaway loops were killed by wall-clock timeout, with the host kernel reported as `4.19.0-gvisor` confirming syscall interposition (Young et al., 2019; NIST, 2017). Yet even a working sandbox is a *research* mode, not the product: it presupposes the very runtime-codegen step that Mode C eliminates, and a container is a soft boundary unless hardened, whereas an allow-list has no residual code-execution surface to harden. The strongest empirical illustration of "bound, don't scan" came from Mode B. The .NET Roslyn semantic analyzer returned a **false negative** for `new System.Net.WebClient` — it references only corelib, so a non-corelib symbol fails to resolve and is silently skipped — while the Rust lexical scanner caught `System.Net` syntactically and rejected it before Roslyn was ever consulted. This concretely demonstrates that post-hoc analysis of free-form code is brittle, and that defence-in-depth (lexical + semantic + consistency + sandbox) — not any single gate — is what makes the C# arm safe. The expressiveness cost of Mode C (only six behaviours) is real, but it is a deliberate and defensible trade for an auditable, on-device end-user tool.

## 8.2 Limitations

The limitations are stated plainly, not in footnotes.

- **The Unity client is verified in the interactive Unity 6 Editor; only headless EditMode tests remain pending.** Mode C and validator-gated Mode A both run live in the Unity 6 Editor — object changes from live backend messages, and model-generated C# compiled at runtime to build structures (§7.5). The drop-in executor's four *headless* batchmode EditMode tests still quit at the **licensing** step (`Access token is unavailable`) — a Unity account sign-in the automation cannot perform, not a code fault — and on-device Quest remains untested for lack of hardware.
- **On-device Quest is argued but not demonstrated.** The deployability claim is structural and strong, but no on-device build or run was performed.
- **gVisor is verified, but the Rust runner is not yet wired to it.** Containment under `runsc` was confirmed, but in those runs the runaway kill was driven by `timeout` on the Docker CLI; the production `DockerSandboxRunner::build_args` does not yet emit `--runtime=runsc`, so the *Rust* runner has only been exercised under plain Docker.
- **The .NET semantic analyzer is deny-list-only and shallow** (see the `System.Net` false negative above), and Mode A is preserved but not integrated into the Rust comparison.
- **Live-microphone speech-to-text is not yet exercised.** The OpenAI language-model path is verified end-to-end with the real gpt-5.5 model (§7.5), and the OpenAI Whisper speech-to-text path is verified at the API level through a text-to-speech-to-text round-trip; what remains is capture from a physical microphone, for which no input device was available.
- **No quantitative or human-subjects study has been conducted**, the system has been verified on a single machine, networking is unauthenticated (per-peer identity remains future work) but now per-peer rate-limited and anti-strobe-throttled, and the Unity client auto-reconnects after a dropped link, the Rust↔C# bounds parity is now guarded by a test but the C# side is still authored by hand, and, because the upstream Ubiq RoomServer `gitpkg` host returns HTTP 402, the RoomServer is vendored into the repository (`vendor/ubiq-roomserver/`) so that verification remains reproducible.

## 8.3 Ethics, privacy and responsible disclosure

DreamCodeVR+ processes push-to-talk voice, which is personal data — and, where it carries biometric voiceprint characteristics, special-category data under the UK GDPR (Articles 9, 25 and 35). The privacy posture is therefore enforced **by construction** rather than promised in prose. No raw microphone audio or transcript is stored; the design intent for any deployment is transcribe-and-delete. The only persisted record is the `observability::TimingEvent` JSONL line, which carries ids, timestamps, decisions, reason-codes and counts but **never** content; a unit test asserts that no `audio`, `transcript`, `secret` or `image` field can appear in that schema, and STT/LLM failures are mapped to fixed reason-codes (`stt_unavailable`, `llm_timeout`, …) so raw detail never leaves stderr. Secrets are held in zeroized `SecretString` wrappers and `.jsonl`/`.env` files are git-ignored.

Because the technology is innovative, involves voice, and may in future involve child users, a **full Data Protection Impact Assessment is treated as a precondition for any user study, not an afterthought**; the relevant University of Birmingham ethics reference and DPIA outcome would be recorded here once obtained. Any human-subjects component — envisaged only as an optional, adults-only red-team exercise — would proceed solely after University of Birmingham ethics approval, with explicit, granular, opt-in consent for any audio capture, a stated retention-and-deletion schedule, and the right to withdraw; age estimation is explicitly out of scope. The sandbox (Mode D) is a security-research artefact for executing deliberately adversarial code, and is framed under **responsible-disclosure** norms: it runs only behind a research flag, in a hardened, network-isolated container, and any escape or evasion finding would be reported to the relevant maintainers before publication (Greshake et al., 2023; OWASP, 2025). Finally, the use of AI assistance during this project is disclosed and conducted in accordance with University of Birmingham policy on generative-AI use, with all load-bearing claims grounded in the verifiable artefact rather than in model output.

# Chapter 9 — Conclusion & Future Work

## 9.1 Contributions

This dissertation set out to make real-time immersive speech programming **safe by construction** and **deployable on a Meta Quest** without discarding the expressive intent of UCL's DreamCodeVR (Giunchi et al., 2024). It delivered: an allow-listed six-action plan DSL whose enum *is* the safety boundary (`behaviour-dsl`); a fail-closed validator that rejects oversized input before parsing and approves iff zero violations remain (`code-policy`); a Rust Ubiq service-peer orchestrator with per-peer sessions, async timeouts, a single spawn-budget chokepoint and privacy-safe telemetry (`unity-transport`, `command-router`, `observability`), including two real protocol-bug fixes found by live testing; a defence-in-depth validated-C# research arm (`csharp-policy` lexical + `roslyn-client` semantic); a sandbox arm verified under both Docker and gVisor (`sandbox`, `services/sandbox-worker`); a safety-preserving personalization/RAG layer that learns user taste from feedback yet injects it only as validator-gated, untrusted guidance (`personalization`); a live observability and runtime-control plane with a web admin panel and on-demand red-team runner (`control`, `admin`); a perceptual and embodied safety layer (a user-frame invariant, scene-relational guards, and temporal envelopes) that extends the safety argument from code to immersive content; a 263-test, `unsafe`-free, panic-averse, supply-chain-audited workspace; an opt-in, age-adaptive dual-plane safety coupling in which a detected minor — or an `Unknown` band, which fails safe to *child* — alone tightens both the code-safety and the perceptual-safety plane (`config::age`, `command-router`), together with two reproducible, numpy-only, CPU-only ML models: a calibrated on-device voice age-*band* gate (band-not-precise-age, emotion deliberately excluded; 17/17 tests) and a continuous ML attack analyzer that red-teams that gate (21/21 tests); and — hardening this baseline under adversarial pressure — an executed 1,057-vector red-team that raised the C# validator's attack-catch rate from 15% to 100% with zero over-blocks, with the whole system demonstrated live end-to-end on a physical Meta Quest (Quest 1/2 Mono sideload).

## 9.2 Answering the research questions

- **RQ1 (safety by construction).** Supported at the architectural and integration level: schema-bounding makes unsafe operations unrepresentable, the validator is fail-closed, and the C# arm's defence-in-depth was shown to catch what its semantic layer missed. An executed adversarial corpus (1,057 vectors) subsequently hardened the C# validator to a 100% attack-catch rate with zero over-blocks (§7.10). The full per-mode quantitative comparison remains future work (§7.7).
- **RQ2 (deployability).** Structurally answered — Mode C removes the runtime-compilation dependency that the IL2CPP/AOT backend forbids (Unity Technologies, 2024). On-device operation has since been demonstrated live on a physical Quest 1/2 Mono sideload (§7.11); the Quest 3 IL2CPP/Store build remains future work.
- **RQ3 (orchestration & performance).** The orchestrator's robustness (per-peer isolation, fail-closed timeouts, no global lock) is verified live through the real RoomServer, and its adversarial robustness was confirmed by the executed red-team (100% of C# attacks and 100 natural-language attacks blocked, §7.10); per-stage latency distributions remain future work (§7.7).
- **RQ4 (comparative trade-off).** The four-mode differential design is specified and the integration arms are verified, but the head-to-head functional, latency and security comparison remains future work (§7.7), and Mode A is not yet wired into the differential harness.

## 9.3 Future work (prioritised)

1. **Quest 3 / Store deployment of Mode C** — the Quest 1/2 Mono sideload (Mode A) is now demonstrated live on-device (§7.11); the remaining step is the IL2CPP/ARM64 Mode-C build for Quest 3 and the Store, plus the four headless EditMode tests and GUI play-mode.
2. **Real STT and LLM** — exercise faster-whisper and OpenAI endpoints under the existing timeout-wrapped paths.
3. **Wire Mode A into the differential harness** for a complete A/B/C/D baseline comparison.
4. **Back the Rust `DockerSandboxRunner` with `runsc`** by emitting `--runtime=runsc` so the production runner inherits the verified gVisor boundary.
5. **Authenticated peer identity for the networking layer.** The self-asserted `peer_uuid` on Ubiq NID frames is the residual that enables cross-peer scene targeting and feedback poisoning. Interim mitigations already reduce the impact — the service peer now sets a per-recipient `target_peer` on every decision so a client applies only decisions addressed to it; the personalization summary is sanitised so forged feedback can no longer inject verbatim instructions (only nudge aesthetic keywords); and per-peer rate limiting bounds flooding — but none authenticates the sender. The full fix is per-peer identity: at join, the service peer issues each client a short-lived, unguessable capability token (or, for non-repudiation, registers a per-peer public key); thereafter a message is accepted as peer *X* only if it carries *X*'s token/signature in the application payload, which is transparent to the RoomServer since it routes opaque frames. On the plaintext TCP channel this must be paired with transport TLS (or a WSS RoomServer) so tokens cannot be captured on the wire. This closes peer impersonation, cross-peer targeting, and feedback poisoning together.
6. **Editor-verify and extend the perceptual-safety layer.** The user-frame invariant, FOV-occlusion, overlap and cumulative-drift guards are implemented in the Unity executor with a cold-start fail-closed fallback (placements are refused when a trusted head pose is unavailable); they require a licensed-Editor compile-and-play pass; they are exercised in-Editor by the `GuardrailSelfTest` harness (13 cases) and are opt-in via `comfortIntensity` (default off for free creation). The reality-aware extension — cross-checking standable, sittable and occluding objects against the Guardian boundary and the passthrough room mesh — and a statistical-model-checking evaluation of the guard automata (after Valluripally et al., 2020) remain.
7. **Add bounds-drift CI** beyond the current parity test (auto-reconnect is now implemented in the Unity Mode-C client).
8. **On-device age gate and continuous analysis.** The age-adaptive coupling (§7.12) and both ML models (§7.13–7.14) are today evaluated on held-out/synthetic audio and a controlled attack corpus with numpy-only models; the outstanding steps are real push-to-talk microphone audio and a physical-Quest run (hardware available from 2026-07-23), the documented wav2vec2 feature upgrade for the age gate, and a live-traffic evaluation of the attack analyzer. Throughout, the platform Meta Quest age-group signal remains the authoritative age source; the ML age band is a secondary safety net and never the legal basis for consent.

## 9.4 Closing statement

The honest balance is that the **design is complete and the backend is proven**, while what remains is **integration and measurement, not redesign**: play-testing the Unity client, exercising real endpoints, and running the differential evaluation end-to-end. The broader claim the work defends is methodological — that for end-user programming in safety-sensitive immersive settings, constraining the output language is a stronger and more deployable safety lever than sandboxing the output, and that it can be enforced by construction rather than by vigilance.
