# DreamCodeVR+: A Static-Admission Defence Against Privacy and Manipulation Attacks in Speech-Driven XR

*Sandeep Rai, University of Birmingham*

> Draft. All quantitative results were produced by the automated evaluation harness (`apps/xr-security-eval`) against the real validator; validator latency is measured directly (§6.5). The evaluation is **static code-admission only**: no generated code was executed, and no Meta Quest headset, camera, passthrough feed, or real sensor was used. Payloads are hand-authored, non-executing source artefacts; any network or file operations they reference target non-routable placeholder hosts and are never performed.

## Abstract

Speech-driven virtual reality (VR) programming lets a user author a scene by talking, with a large language model (LLM) generating C# that is compiled and executed live inside the headset. This convenience is also an attack surface: if malicious code runs unchecked, it can read the user's body, attempt to access the outward-facing cameras that image the user's surroundings, or physically manipulate the user. We characterise five concrete "speak-to-C#" attack classes — three privacy classes (biometric capture, positional/motion exfiltration, and attempted access to environment-imagery / outward-camera APIs) and two embodied-manipulation classes (the human-joystick and tampering with the guardian safety boundary) — and introduce a Rust safety backend that validates every generated fragment before it can execute, refusing anything unsafe (fail-closed). The validator reconstructs dotted API names to defeat lexical evasions and matches them against layered denylists. Using an automated, offline **static code-admission** evaluation over 40 hand-authored adversarial payloads (representative of code an LLM-enabled pipeline could emit) and 12 benign controls, we measure the malicious-payload pass rate before and after defence: under the DeployHardened profile the pass rate falls from 100.0% to 5.0% — a **95.0% static code-admission rejection on the curated 40-case benchmark** — while all 12 benign creative tasks remain admitted. We also measure the validator's per-call latency (median 84.9 µs; §6.5). Crucially, code-security filtering alone leaves pure XR manipulation almost untouched, motivating layered perceptual defences.

# 1. Introduction

Speech-driven "speak-to-build" programming promises to make virtual-reality (VR) authoring immediate and inclusive: a user describes a change in natural language, a large language model (LLM) translates that intent into C#/Unity source, and the code is compiled and executed live inside the headset so that the scene changes in place. DreamCodeVR+ extends one such system — the speech-driven VR programming system of Giunchi et al. (2024) — in exactly this spirit. The power of the paradigm, however, is inseparable from its danger. When an LLM writes runnable code straight into a live, embodied session, the system inherits two distinct classes of risk at once.

The first is the familiar risk of executing untrusted, machine-generated code. An LLM can be prompted, or can simply drift, into emitting code that touches the file system, the network, reflection, process control, or persistent storage — a concern reflected in emerging guidance on LLM-application security (OWASP, 2023) and in datasets built to measure insecure code generation (Siddiq & Santos, 2022). The second risk is specific to XR and is not captured by conventional code-safety thinking at all: harm mediated by the headset's sensors and actuators. VR platforms continuously capture the body — cameras, microphone, eye gaze, hand skeleton, head and hand pose, and passthrough imagery of the user's real room — and this telemetry is richly identifying. Nair et al. (2023a) show that private personal attributes can be inferred from head and hand motion, and Nair et al. (2023b) uniquely re-identify more than 94% of a population of over 50,000 users from motion data alone. Beyond privacy, the same immersive channel can be turned against the user's body: Casey et al. (2021) demonstrate "human-joystick" attacks that rotate or translate the virtual world to physically herd a user toward a real wall or door, and manipulation of the chaperone/guardian boundary that is meant to keep the user safe. A speak-to-code system that admits such code does not merely leak data or crash — it can steer a person in physical space.

These two risk classes have been studied largely in isolation, and neither has been addressed for the specific setting of an LLM that writes executable code into a live XR session. Code-generation safety work targets conventional software, not embodied harm; the XR-attack literature characterises the threats but assumes a conventional application, not one whose behaviour is authored on the fly by an LLM. There is, to our knowledge, no combined defence — one that guards against both code-execution and XR-perceptual harm — coupled with an evaluation that quantifies how much of the attack surface such a defence actually rejects at admission for a speak-to-code XR system. This paper addresses that gap.

We make three contributions:

1. **A taxonomy of five XR attack classes, realised as concrete speak-to-code exploits.** We organise the threat into three privacy classes — biometric capture and positional/motion exfiltration, grounded in Nair et al. (2023a, 2023b), and attempted access to environment-imagery / outward-camera APIs — and two manipulation classes grounded in Casey et al. (2021), the human-joystick and the chaperone/boundary attack. Each class is instantiated not abstractly but as **hand-authored `GeneratedBehaviour : MonoBehaviour` payloads representative of code an LLM-enabled pipeline could emit** in response to a spoken instruction, yielding a curated corpus of 40 adversarial payloads (five classes of eight) alongside 12 benign creative controls.

2. **A fail-closed static-admission defence backend.** We introduce a Rust safety layer that validates every generated C# fragment *before* it can execute and refuses anything unsafe by default. It combines lexical and structural analysis — a tree-sitter C# parse whose syntax tree is walked by custom logic that reconstructs dotted API names to defeat whitespace, comment, `global::`, verbatim-`@`, `\uXXXX`, and using-alias evasions — with denylist matching, a single-`MonoBehaviour` constraint, and a size cap. The backend exposes two hardening profiles: a security-only profile (CreativeFreedom) that blocks system- and network-access APIs, and the DeployHardened profile that adds a perceptual/XR-device denylist covering cameras, tracking, boundary, and XR subsystem interfaces.

3. **An automated, local, before/after static-admission evaluation.** Adopting a code-admission methodology in the spirit of SecurityEval (Siddiq & Santos, 2022), we submit every payload to the *real* validator at three defence levels — no defence, security-only, and DeployHardened — and record whether the malicious code is statically rejected before it could run. The evaluation is deterministic, offline, and requires no Meta Quest headset; a payload "passes" if it is admitted and would have executed. We additionally report the validator's measured per-call latency (§6.5).

The headline result is a steep, layered reduction in admitted attacks. The overall malicious-payload pass rate falls from 100.0% with no defence, to 62.5% under the security-only profile, to 5.0% under DeployHardened — a 95.0% static code-admission rejection (38 of 40 payloads rejected on the curated 40-case benchmark) — while all 12 benign creative controls, including dual-use mixed-reality authoring, are admitted at every level, so creative freedom is preserved. Crucially, the middle column exposes *why* the layers are necessary: a code-security filter alone rejects the payloads whose exfiltration relies on system and network APIs, but almost entirely misses pure XR manipulation, because those payloads reference no system API. Under security-only, human-joystick payloads still pass at 100.0% and chaperone at 87.5%; only the perceptual/XR layer rejects them. Defences for speak-to-code XR must therefore be layered. We report our results honestly, including a residual of two human-joystick payloads that are lexically indistinguishable from legitimate authoring and can only be caught at runtime — a limit of any static, headset-free defence, which we make explicit rather than obscure.

## 2. Background & Threat Model

### 2.1 The speak-to-code XR pipeline

DreamCodeVR+ extends a speech-driven VR programming system (Giunchi et al., 2024) in which the user authors an immersive scene by talking to it. A spoken utterance ("build a snowman", "recolour the house") is transcribed and handed to a large language model (LLM), which emits C#/Unity source. That source is not merely displayed or logged: it is compiled and executed live inside the headset, where it takes effect as a change to the running scene. The generated fragment is, by construction, a single `GeneratedBehaviour : MonoBehaviour` that the engine instantiates and runs.

The very property that makes this pipeline compelling — direct manipulation of a live scene by voice, with no edit-compile-redeploy cycle — is what makes it dangerous. Unlike a conventional application, whose executable behaviour is fixed when it ships, here the executable surface is synthesised on demand from untrusted natural language and run in place. The generated code executes with the full privileges of the host application: absent any restriction it can reach the platform's system and network APIs (file, socket, process, reflection) and the engine's XR-device APIs (passthrough and eye cameras, microphone, head and hand tracking, haptics, and the guardian boundary). Runtime code generation is therefore the attack surface. Whoever can influence what the model writes can, in effect, cause arbitrary code to run inside a device strapped to the user's face and body.

### 2.2 Adversary model

We treat the LLM as untrusted. The user's spoken request flows into the model's prompt, and the model's output is executable; a model that is compromised, poisoned, or steered by prompt injection can therefore emit malicious C# in place of — or interleaved with — the benign scene code the user asked for (OWASP, 2023). Our threat is precisely this: adversarial code that arrives through the legitimate generation channel and would run if admitted. We do not assume the attacker can modify the validator, the game engine, or the underlying platform; the sole adversarial channel is the source the model produces. Each attack is realised as one such `GeneratedBehaviour : MonoBehaviour`. The defender's task reduces to a single admission decision made before execution: for every generated fragment, admit it only if it is safe, and otherwise refuse it (fail-closed).

### 2.3 Attack classes

We organise the threat into five classes along two axes of harm — privacy (data leakage from the user's body and surroundings) and manipulation (embodied safety, in which the immersion itself is used to act on the physical user). Each class is instantiated as concrete speak-to-C# exploits.

**Privacy — data leakage.** VR headsets are dense sensor platforms, and their motion and sensor streams are far from anonymous. Nair et al. (2023a) show that private personal attributes can be *inferred* from head- and hand-motion data alone, and Nair et al. (2023b) show that such data are *identifying*: they re-identify over 94% of a population of more than 50,000 users from head and hand motion. Against this backdrop we distinguish three privacy classes:

- **(a) Biometric.** Code that reads the body — passthrough or eye camera, microphone, eye-gaze, hand skeleton, and haptics. The modelled harm is capture of raw biometric signals that support both attribute inference and identification (Nair et al., 2023a, 2023b).
- **(b) Positional / motion.** Code that exfiltrates head and hand pose. The modelled harm is re-identification and cross-session tracking of the wearer from motion telemetry — the exact signal shown to be uniquely identifying at scale (Nair et al., 2023b).
- **(c) Environment-imagery / outward-camera API access.** Code that *attempts to access* the outward-facing (passthrough) cameras or the spatial-map API in order to image the user's physical surroundings. We treat this class as **attempted access to environment-imagery and outward-camera APIs**; the modelled harm is leakage of the user's private surroundings rather than of the user's body. We did not capture, transmit, or test against any real camera feed, passthrough imagery, or physical room: the payloads are static source that *reference* these APIs, and are evaluated only for whether the validator admits them. This class is not attributed to Nair et al., whose work concerns motion inference.

**Manipulation — embodied safety.** Because the headset mediates the wearer's entire visual frame and enforces their real-world safety boundary, code that controls those surfaces can act on the physical person, not merely their data. Casey et al. (2021) demonstrate this directly:

- **(d) Human-joystick.** Code that rotates or translates the virtual world so that, chasing a moving scene, the user is physically herded across the room — into a real wall, a door, or a hazard (Casey et al., 2021). The modelled harm is bodily, and the attack need reference no system or network API: it manipulates ordinary engine transforms.
- **(e) Chaperone / boundary.** Code that moves or disables the guardian safety boundary, stripping away the warning that keeps the user inside a safe play space — the "Man-in-the-Room" manipulation of Casey et al. (2021). The modelled harm is the removal of a physical-safety guarantee.

The two axes differ in more than harm. The privacy classes reach outside the ordinary authoring vocabulary — to system, network, and device-access APIs — whereas the manipulation classes can be expressed entirely in the same engine primitives a legitimate scene-builder uses. This asymmetry, foreshadowed here and quantified in our evaluation, is what motivates a layered defence rather than a single code-security filter.

## 3. Related Work

Our contribution sits at the intersection of three literatures that have so far developed largely in isolation: (i) demonstrated privacy and safety attacks against extended-reality (XR) systems, (ii) safety guardrails and admission-style evaluation for LLM-generated code, and (iii) perceptual and embodied safety thresholds for immersive media. We review each in turn and then position our work.

### 3.1 XR privacy and security attacks

A growing body of work shows that the sensor-rich nature of XR makes it a potent privacy surface. Nair et al. (2023b) demonstrate that head- and hand-motion telemetry alone is sufficient to uniquely re-identify individual users at scale, correctly re-identifying over 94% of a population of more than 50,000 users from motion data. In a companion study, Nair et al. (2023a) show that the same class of motion data supports the inference of private personal attributes rather than mere identity. These results establish that the positional and biometric data streams available inside a headset are not benign telemetry but a direct re-identification and attribute-inference channel; they ground the biometric and positional/motion attack classes we consider. The environment-imagery / outward-camera class concerns attempted access to the outward-facing camera and spatial-map APIs rather than motion inference, and we do not attribute it to Nair et al.

Beyond passive data leakage, Casey et al. (2021) show that XR systems are vulnerable to active, embodied manipulation. Their "human joystick" attack covertly translates and rotates the virtual world to physically herd a user across a real room, and their Man-in-the-Room / chaperone manipulations tamper with the guardian safety boundary. These attacks are notable because they threaten the user's physical safety rather than their data, and — as we later show — because they need not reference any system or network API, which places them outside the reach of conventional code-security filters. Casey et al. (2021) grounds the manipulation attack classes we evaluate (human-joystick and chaperone/boundary).

Together, this strand establishes that the attacks are real and physically grounded. What it does not provide is a defence for systems that synthesise and execute code from untrusted input, which is the setting our work addresses.

### 3.2 LLM code-generation safety and admission-style evaluation

The second strand concerns the safety of code produced by large language models. The OWASP Top 10 for Large Language Model Applications (OWASP 2023) codifies insecure output handling and over-reliance on unvalidated model output as first-class risks, arguing that generated artefacts must be treated as untrusted and validated before use. On the evaluation side, SecurityEval (Siddiq & Santos 2022) established the practice of assessing model-generated code by checking, per prompt, whether the emitted code contains a disallowed or vulnerable construct rather than only whether it is functionally correct. Our before/after static code-admission evaluation follows this admission-oriented spirit: for each payload we ask whether the validator statically rejects the code before it can run, at each defence level.

This literature motivates static validation of LLM output as an active concern, but it is framed around conventional software vulnerabilities (e.g., injection, unsafe deserialisation) and general-purpose code. It does not address XR-specific harms — motion exfiltration, outward-camera access, or embodied manipulation — nor does it consider a speech-to-code pipeline in which the generated artefact is a Unity MonoBehaviour compiled and executed live inside a headset.

### 3.3 Perceptual and embodied safety thresholds

A third, older strand recognises that immersive and animated media can harm users through their perceptual and physical effects rather than through data. The Web Content Accessibility Guidelines (W3C 2023), criterion 2.3.1, specify a three-flash-per-second threshold to protect against photosensitive seizures. Although drawn from the web and accessibility domain, this establishes a precedent that rendered output — not only code and data flows — can constitute a safety hazard with quantifiable thresholds, and it motivates treating perceptual and embodied effects as a distinct safety dimension alongside code and data security. This framing informs the perceptual/XR-device layer of our hardened profile, which targets device and rendering surfaces that a purely code-security filter overlooks.

### 3.4 Positioning

Each strand supplies part of the picture: the XR-security literature shows the attacks are real and physically grounded (Nair et al. 2023a, 2023b; Casey et al. 2021); the LLM-safety literature argues that generated code must be validated and evaluated by admission (OWASP 2023; Siddiq & Santos 2022); and the accessibility literature establishes perceptual harm as a measurable safety dimension (W3C 2023). To our knowledge, however, no prior work combines a concrete, fail-closed defence with an automated before/after static-admission evaluation for a speak-to-code XR system such as the one we extend (Giunchi et al., 2024). We contribute exactly this pairing: a static-admission validator for generated C# and a deterministic, offline code-admission evaluation of it against XR privacy and manipulation attacks at graduated defence levels. Consistent with the honesty of our reporting, we do not claim that static admission captures on-device physical execution; a residual class of manipulation payloads is lexically indistinguishable from legitimate authoring and is deferred to runtime enforcement, which we report transparently in the sections that follow rather than obscuring here.

## 4. System & Defence

DreamCodeVR+ extends a speech-driven VR programming system in which a user speaks an intention, a large language model (LLM) emits C#/Unity source, and that source is compiled and executed live inside the running scene (Giunchi et al., 2024). This pipeline is powerful precisely because it grants natural language a direct path to code execution, and that is also its hazard: an LLM is an untrusted code generator whose output cannot be assumed benign. The contribution of this work is a safety backend, written in Rust, that sits between generation and execution and validates every generated program *before* it is admitted to compilation. The backend is designed to be **fail-closed**: a program is admitted only if it passes validation, and anything that cannot be positively shown to be safe — including inputs the validator cannot parse or reason about — is refused. Equally, the design is intended to be **creative-freedom-preserving**: the goal is to reject exploits without rejecting legitimate authoring, so that the expressive core of the system survives.

### 4.1 Lexical and structural validation

The validator combines lexical and structural analysis over the concrete syntax of the candidate program. Rather than operate on raw text — which is brittle and trivially evaded — it parses each program with a tree-sitter C# grammar into a syntax tree, and applies custom logic that walks that tree (the denylist policy is not performed by tree-sitter; it is hand-written Rust over the parse tree). Two complementary checks are applied.

**Structural checks.** The generated artefact is required to be exactly one `MonoBehaviour` subclass (the `GeneratedBehaviour : MonoBehaviour` contract the runtime expects), so that the admitted code conforms to the narrow shape the host is prepared to instantiate and cannot smuggle in additional top-level types. A size cap bounds the length of the accepted program, limiting both compilation cost and the surface available for obfuscation. These are cheap invariants that constrain the space of admissible programs before any semantic reasoning begins.

**Dotted-name reconstruction.** The core of the check is a denylist match against fully qualified, dotted API names — but a naive textual match on names such as `System.IO` is defeated by a range of source-level evasions. The validator therefore reconstructs each dotted invocation from the parse tree so that the *resolved* name, not its surface spelling, is what is matched. This defeats: interposed **whitespace** and **comments** between identifier and member; the `global::` root qualifier; the `@`-prefixed **verbatim** identifier form; `\uXXXX` **Unicode escapes** in identifiers; and **`using`-alias** indirection that renames a banned type before use. By canonicalising names ahead of the match, an attacker cannot hide a banned API behind lexical noise or aliasing; the check sees the API the code would actually bind to at compile time. (This canonicalisation depends on the parser surfacing a qualified-name/member-access node; call sites that never surface a namespace node are covered by the identifier denylist instead — an honest coverage boundary the implementation documents.)

### 4.2 Two hardening profiles

The validator ships with two denylist profiles, reflecting two deployment postures.

**CreativeFreedom (security-only).** The always-on profile targets *system access* — the capabilities an exploit needs to reach off the device or out of the sandbox. Its denylist covers the `System.IO`, `System.Net`, `System.Reflection`, `System.Diagnostics`, `System.Threading` and `System.Runtime.InteropServices` namespaces and `Application.Quit`, together with identifiers such as `Process`, `Assembly`, `DllImport`, `Marshal`, `UnityWebRequest`, reflection verbs and `PlayerPrefs`, among others. This profile blocks the file, network, process, reflection and persistence primitives through which data are exfiltrated or the host is subverted, while leaving the ordinary Unity scene-authoring API untouched.

**DeployHardened.** The hardened profile is a strict superset: it retains the entire system-access denylist and adds a *perceptual / XR-device* layer aimed at the sensors and world-model surfaces specific to immersive hardware. This adds `WebCamTexture`; the Oculus device surface (`OVRManager`, `OVRBoundary`, `OVRPlugin`, `OVRInput`, `OVRHaptics`, `OVRCameraRig`); the tracking and XR-subsystem surface (`InputTracking`, `TrackedPoseDriver`, `XROrigin`, `XRSettings`, `XRDevice`, `InputDevices`, `XRInputSubsystem`); and the `UnityEngine.XR` namespaces. These are the APIs through which a program reads the body and the room — cameras, boundary/guardian, pose and input devices — and which therefore mediate the privacy and manipulation attacks that reference no system API at all. The two profiles thus separate two distinct concerns: keeping data and control inside the device (CreativeFreedom) versus governing what the immersive hardware may sense and actuate (DeployHardened).

### 4.3 Three evaluation levels

The same defence is exercised at three escalating levels, so that the marginal contribution of each layer can be isolated:

- **Level 0 — no defence:** the original system would execute LLM-generated code unvalidated; this is the baseline threat surface. (In the evaluation, no code is executed; level 0 is modelled as "the validator is not invoked", so every payload is admitted.)
- **Level 1 — security-only:** the CreativeFreedom profile is enforced (system-access bans only).
- **Level 2 — DeployHardened:** the DeployHardened profile is enforced (system-access *plus* perceptual/XR-device bans).

Each candidate program is submitted to the *real* validator at levels 1 and 2 and the admission decision is recorded — whether the code would be statically rejected before it could run. This is a code-admission evaluation, in the spirit of security-oriented code-generation benchmarks such as SecurityEval (Siddiq & Santos, 2022): it is deterministic, local and offline, and it measures whether an exploit is *admitted*, not its physical effect on a headset. That scoping is deliberate and is revisited in the limitations: the evaluation certifies what the static backend will and will not let execute, and the residual it cannot resolve statically — attacks that are lexically indistinguishable from legitimate authoring and require runtime enforcement — is reported transparently rather than hidden by the choice of metric.

## 5. Evaluation Methodology

### 5.1 Evaluation corpus

We evaluate against a corpus of 52 speech-driven programming episodes: 40 adversarial payloads and 12 benign creative controls. Each payload is a complete `GeneratedBehaviour : MonoBehaviour` C# class of exactly the form the base system produces — **hand-authored, and representative of code an LLM-enabled pipeline could emit** in response to a spoken instruction (Giunchi et al., 2024). The corpus therefore exercises the validator on the kind of input it must defend in deployment, while being fully deterministic and independently re-runnable.

The 40 adversarial payloads are organised as five attack classes of eight payloads each, following the threat model above. Two of the three privacy classes — biometric body capture and positional/motion exfiltration — are grounded in the demonstrated inference and re-identification attacks of Nair et al. (2023a, 2023b), in which head- and hand-motion traces alone suffice to infer private personal attributes and to uniquely re-identify individual users at scale. The third privacy class, environment-imagery / outward-camera API access, concerns *attempted access* to outward-facing camera and spatial-map APIs; no real camera feed, passthrough imagery, or physical room was captured or used. The two manipulation classes — the human-joystick attack and the chaperone/boundary attack — are grounded in Casey et al. (2021). Within each class the eight payloads vary the concrete API surface referenced and the evasion technique employed, so that each class is represented by a family of realisations rather than a single canonical example. The payloads are hand-authored, drawing on the attack literature cited above and on the real validator fixtures used during development; we therefore treat them as a demonstration of the five classes and their evasions, not as an exhaustive sample of the attack space (see Limitations).

The 12 benign controls are ordinary creative requests of the kind the system is built to serve — for example, building a house or a snowman, recolouring an object, and dual-use mixed-reality authoring tasks. These controls let us measure whether hardening preserves the system's intended function, that is, whether legitimate creative code continues to be admitted unchanged.

This 40-attack + 12-benign benchmark is authored specifically for the XR-privacy-and-manipulation surface studied here. The broader project separately maintains a 128-vector attack *taxonomy* and a distinct automatically-generated store of 164 records; these are natural-language vector sets organised into five families (network-identity, generated-code, voice-and-sensor, privacy/PII, immersive). The 40 C# payloads used here are authored independently for this evaluation and are *not drawn from* those sets — they share a threat-model framing, not vector membership. Two of the taxonomy families (network-identity and generated-code) are outside the XR privacy/manipulation scope of this paper and are not exercised by the 40-case benchmark.

### 5.2 Static code-admission evaluation

We adopt a code-admission methodology, in the spirit of static security-dataset evaluations such as SecurityEval (Siddiq & Santos, 2022). For each payload we invoke the real validator — the same Rust implementation used at runtime, not a model or a reimplementation of it — and record its admission decision. A payload is either **statically rejected** (refused before it can execute, consistent with the system's fail-closed posture) or **admitted** (it would be compiled and run).

Each payload is evaluated at three defence levels: (0) no defence, in which the validator is not invoked and every payload is admitted; (1) security-only, the CreativeFreedom profile comprising the always-on system-access denylist; and (2) DeployHardened, which adds the perceptual/XR-device denylist. The three levels let us attribute rejection to specific layers of the defence rather than to the defence as a whole.

We report the **malicious-payload pass rate**: the fraction of adversarial payloads that are *not* statically rejected at a given level — i.e., that would be admitted for compilation and execution (lower is better). The complementary figure, the fraction statically rejected, we call the **static code-admission rejection rate**. For the benign controls we report the over-block rate — the fraction of legitimate payloads wrongly refused — as the complementary measure of the cost of hardening. An ideal defence drives the adversarial pass rate toward zero while holding benign over-block at zero.

### 5.3 Determinism, and what the metric does and does not measure

Because the validator performs a deterministic lexical and structural analysis, every decision is reproducible: a given payload at a given defence level yields the same admission outcome on every run. The entire evaluation is executed locally and offline — no network service, no LLM inference, and, by design, no Meta Quest headset. The payloads are **static source artefacts and are never executed**: any file or network operation they reference (e.g., a `UnityWebRequest`, a socket, or a file write) is never performed, targets non-routable placeholder hosts, and accesses no real sensor; the class labels (e.g., "exfiltration") describe the *intended* behaviour of the code, not an action taken during evaluation.

We are explicit about the semantics of this metric. Code-admission measures whether an exploit is admitted for execution, not the physical effect it would have on a headset. A payload counted as "rejected" is one the validator refuses; a payload counted as "passing" is one that would be permitted to run, which under the modelled threat would produce the corresponding privacy or manipulation effect, but we do not observe that effect on-device. **Static admission does not demonstrate runtime prevention.** This scoping is deliberate — it isolates the contribution of static validation — but it also bounds our claims: attacks whose realisation is lexically indistinguishable from legitimate authoring cannot be separated by static admission alone and require runtime enforcement, which we report transparently and revisit under Limitations.

All results are deterministic, local, and offline; they measure whether an exploit is admitted, not its physical effect on a headset.

### 6.3 The layered-defence finding

The overall drop to 62.5% under security-only masks a sharp split between the two threat families. The privacy/exfiltration classes are partially rejected by the always-on system/network denylist, because their leakage paths reference system, network, or reflection APIs: the biometric pass rate falls from 100.0% to 37.5%, positional/motion from 100.0% to 62.5%, and environment-imagery/outward-camera from 100.0% to 25.0% at security-only. The manipulation classes, by contrast, are almost untouched at that level: the human-joystick pass rate remains at 100.0% and chaperone/boundary at 87.5% under security-only, because these payloads reference no system API and so trip no exfiltration ban. Only the perceptual/XR layer rejects them — enabling it drops chaperone/boundary to 0.0% and human-joystick to 25.0% under DeployHardened. This is the central result: a code-security filter alone rejects privacy exfiltration but misses pure XR manipulation, so defences must be layered.

### 6.4 Honest residual

Two of the 40 payloads are not rejected even under DeployHardened, which is the entire residual behind the overall 5.0% and the 25.0% remaining for human-joystick (2/8). Both are human-joystick payloads (joy-05, joy-06) that rotate or translate `Camera.main.transform`. This operation is lexically indistinguishable from legitimate camera authoring, so static validation cannot reject it without also rejecting creation. Rejecting these two attacks requires runtime enforcement (a UserFrameGuardian or sandbox that constrains frame-of-reference changes during execution), which is out of scope for this static, headset-free evaluation and is reported transparently rather than counted as rejected.

### 6.5 Validator latency

Because the validator is invoked once per generated command, we measured its per-call latency directly. We timed the `DeployHardened` static-admission check over the 52 corpus payloads with 300 discarded warm-up passes followed by 3,000 timed repetitions per payload (**156,000 timed calls**), each call bracketed by a monotonic clock. Measurements were taken on an **AMD Ryzen 5 5500U** (x86-64, Linux 7.0.0), compiled with **rustc 1.96.0 in the `release` profile**.

| Statistic | Latency |
|---|---|
| median (p50) | 84.9 µs |
| mean | 97.1 µs |
| p95 | 235.4 µs |
| p99 | 303.5 µs |
| max | 3,159.6 µs |

The median per-command admission check is therefore sub-millisecond (84.9 µs), and even the p99 is ~0.3 ms. The reported maximum (3.16 ms here) is a single-sample tail value consistent with an OS-scheduling outlier; unlike the stable central percentiles, it varies run to run (we have observed maxima up to ~6.6 ms across repeated runs) and should not be read as a hard bound. This cost is negligible relative to the LLM generation and Unity compilation stages of the pipeline (typically seconds), so the validator can be run inline before execution without a perceptible penalty. We deliberately do *not* claim an end-to-end real-time *system* result: the pipeline's dominant latencies (speech recognition, LLM inference, runtime compilation) are not measured here, and no on-device timing was performed.

# 7. Discussion

Our findings support a single organising claim: for a system in which an LLM writes runnable code that is compiled and executed live inside a headset, code security is necessary but not sufficient, and XR safety must be constructed in layers. Below we interpret the evidence, then state plainly what this static, headset-free evaluation does and does not establish.

## 7.1 A code-security filter is necessary but insufficient

Moving from no defence to the security-only profile (CreativeFreedom) reduces the overall malicious-payload pass rate from 100.0% to 62.5%, and the DeployHardened profile reduces it further to 5.0% — a 95.0% static code-admission rejection (38/40). The first layer clearly matters. But the decomposition by attack class shows why it cannot stand alone. Under security-only, the two manipulation classes are barely touched: human-joystick stays at 100.0% and chaperone at 87.5%. This is not a tuning artefact — it is structural. Human-joystick and chaperone attacks physically herd the user or disable the guardian boundary (Casey et al., 2021) without referencing any system or network API, so a denylist built around System.IO/Net/Reflection/Diagnostics and network egress has nothing to match against. Only the perceptual/XR-device layer added in DeployHardened — banning the OVR* device APIs, tracking and XR-subsystem APIs, and the UnityEngine.XR namespaces — brings these classes down (chaperone to 0.0%, joystick to 25.0%). The layered-defence result is therefore the central takeaway: a code-security filter is a genuine and necessary first line, but an entire attack family (embodied manipulation) is invisible to it and requires a distinct perceptual/embodied layer.

## 7.2 Privacy and manipulation are governed by different mechanisms

The class-level numbers also show that privacy and manipulation are rejected by different bans, and that "privacy" itself is not monolithic. Under security-only, the privacy classes are only partially reduced (biometric 37.5%, positional 62.5%, environment-imagery/outward-camera 25.0% still pass), not eliminated. The security-only layer catches the exfiltration path — where data would leave the device through system or network APIs — but many privacy reads never reference those APIs: a biometric or positional read that only queries the tracking/eye-gaze/hand-skeleton device surface, or an outward-camera/spatial-map access that only touches the camera-device surface, survives until the device-API denylist in DeployHardened removes it. In other words, transport is governed by the security layer, whereas sensor-API access itself is governed by the perceptual/device layer. Manipulation sits even further from the security layer: it references no system API at all, so it is essentially a device-layer (and, in the residual case below, a runtime) concern. This clean separation — exfiltration bans for the "data leaving" step, device-API bans for the "sensing the body/room" and "moving the world" steps — is why the two hardening profiles are complementary rather than redundant. The privacy classes are grounded in the demonstrated inference and re-identification power of VR motion data (Nair et al., 2023a; Nair et al., 2023b), and the manipulation classes in the human-joystick and chaperone/Man-in-the-Room attacks (Casey et al., 2021); our contribution is to show that a defence must reach both surfaces to cover both threat families.

## 7.3 Safety without crippling expressiveness

Hardening is worthless if it destroys the creative premise of the base system (Giunchi et al., 2024), in which a user speaks and the world changes. The benign controls address exactly this concern: 12/12 benign creative payloads are admitted at every defence level, including DeployHardened, with 0/12 over-blocked (100.0% pass). Critically, this holds for dual-use mixed-reality authoring — content that legitimately shapes the scene and would be the natural target of an over-eager filter. The result indicates that the denylists are drawn tightly enough around the abusive API surface to leave ordinary creative expression intact: safety is bought here without a measured expressiveness cost on this corpus. We temper this only by noting that 12 controls demonstrate preservation of the studied creative patterns, not the full space of things a user might say.

## 7.4 The honest residual: a runtime guardian as defence-in-depth

Two of the forty attacks are not rejected even at full hardening: joy-05 and joy-06 rotate and translate `Camera.main.transform` to induce human-joystick motion. These are lexically indistinguishable from legitimate authoring — moving or reorienting the camera is exactly what a creator asks for when building a scene — so a static, lexical/structural validator cannot reject them without also rejecting creation, which would violate the expressiveness result above. This residual is not a gap to be papered over but a signpost: it delineates precisely the boundary of static admission control and motivates a complementary runtime layer. A runtime enforcement component (a UserFrameGuardian or sandbox that bounds induced locomotion and camera reframing at execution time) is the natural third layer of the defence-in-depth stack, catching at runtime what is undecidable at parse time. It is deliberately out of scope for this static, headset-free evaluation, and we report the two residual vectors transparently rather than adjusting the corpus to hide them.

## 7.5 Generality

The taxonomy (five XR attack classes across privacy and manipulation, each realised as a concrete speak-to-C# exploit) and the code-admission evaluation method (in the spirit of SecurityEval; Siddiq & Santos, 2022) are not specific to this validator or this base system. They apply to any pipeline in which a language model emits code that is then compiled and run — the "insecure output handling / excessive agency" hazard framed for LLM applications generally (OWASP, 2023) — deployed in an XR context where the output can read the body, access outward cameras, or move the user. The evaluation is deterministic, local, and offline, which makes it a cheap regression harness that a comparable system can adopt by supplying its own validator and payloads. Finally, the perceptual/embodied dimension surfaced here is broader than the device-API access we currently gate: content-level perceptual harms — for example, flashing that exceeds the three-flash threshold of WCAG 2.1 §2.3.1 (W3C, 2023) — represent a further axis that neither the security layer nor the current perceptual layer addresses, and that a fuller perceptual-safety treatment would need to cover. We therefore present these results as evidence for a layered architecture and a transferable method, not as a claim of completed safety.

## 8. Limitations, Future Work & Conclusion

### 8.1 Limitations

**Static code-admission, not on-device physical effect.** Our evaluation measures code *admission*: for every payload we invoke the real Rust validator at each defence level and record whether the malicious C# is statically rejected before it could run, in the spirit of admission-oriented security benchmarks such as SecurityEval (Siddiq & Santos, 2022). It therefore quantifies whether an exploit is *admitted*, not the physical effect an admitted payload would have on a headset, and static admission does not by itself demonstrate runtime prevention. This is deliberate: the study is deterministic, local and offline, and uses no Meta Quest, no camera, and no real sensor. The price of that choice is that any harm which manifests only at runtime falls outside what a static validator can certify — most concretely the residual described next.

**Honest residual (2/40).** Two human-joystick attacks, joy-05 and joy-06, rotate and translate `Camera.main.transform`. These operations are lexically indistinguishable from legitimate scene authoring — the same call is exactly what a user requests when they ask to turn or move the viewpoint — so a static, lexical/structural validator cannot reject them without also rejecting creation. We report them transparently rather than claim a rejection we do not have. This is why the static code-admission rejection at DeployHardened is 95.0% (38/40) rather than 100%: the joystick class remains at 25.0% pass rate even fully hardened. Closing this gap requires runtime enforcement (a UserFrameGuardian or sandbox that bounds cumulative viewpoint displacement), which is out of scope for a static, headset-free evaluation.

**Hand-authored corpus.** The 40-attack corpus (five classes × eight) is hand-authored, grounded in the XR-attack literature — motion-based attribute inference and re-identification (Nair et al., 2023a; 2023b) and the human-joystick and chaperone/Man-in-the-Room manipulations (Casey et al., 2021) — and in the validator's own fixtures. It is constructed to *demonstrate* the five attack classes, not to exhaust them; the reported rates characterise the classes as realised here rather than a complete attack surface. The environment-imagery / outward-camera class is evaluated as *attempted API access*: no real camera feed, passthrough imagery, or physical surroundings were captured or tested.

**Single validator configuration.** All results are for a single validator configuration — one denylist set and one tree-sitter grammar. We do not vary the denylists or the parser, so the admission rates should be read as evidence for this configuration rather than a general bound. Because the corpus is hand-authored, this study does not exercise any specific LLM, prompt, or model, and makes no claim about the rate at which a given model emits insecure code.

### 8.2 Future work

**An independently authored holdout evaluation.** The single most important next step for external validity is an *independently authored holdout corpus*: a fresh set of adversarial and benign payloads written by a party who does not see the validator's denylists, used strictly once for evaluation. To avoid the overfitting that undermines self-authored benchmarks, the validator must not be tuned against the holdout, and the holdout results must not feed back into the denylists. **We deliberately do not construct such a holdout, generate holdout results, or tune the validator against one in this paper**; doing so within the same effort that authored both the attacks and the defence would risk exactly the leakage this proposal is meant to avoid. We flag it as the primary future evaluation precisely so that it is done independently.

**Runtime UserFrameGuardian evaluation.** The second step is a runtime enforcement layer, and a corresponding *runtime* evaluation, that closes the 2/40 residual. Because joy-05 and joy-06 are indistinguishable from legitimate authoring at the token level, they must be caught while executing — a UserFrameGuardian that observes and bounds cumulative camera translation and rotation would convert an admitted-but-unsafe viewpoint manipulation into a runtime refusal, complementing rather than replacing the static filter. Evaluating it requires executing payloads (on a headset or in a runtime harness), which is outside the static, offline scope of this study.

**On-device and content-level extension.** Finally, running admitted and rejected payloads on a real headset would measure the physical effect this study cannot — directly validating that rejected exploits are indeed prevented and that admitted residuals behave as the static analysis predicts. The perceptual/XR layer could also be extended from API denylisting towards content-level bounds, for example enforcing the WCAG 2.1 three-flash threshold (W3C, 2023) against seizure-inducing rendering.

### 8.3 Conclusion

Our central result is that defences must be *layered*. A code-security filter alone (CreativeFreedom) rejects privacy *exfiltration*, because those attacks reference system and network APIs, but it misses pure XR *manipulation*: under security-only the human-joystick class still passes at 100.0% and chaperone at 87.5%, since neither references a system API. Only the perceptual/XR denylist of DeployHardened rejects them, driving the overall malicious-payload pass rate from 100.0% (no defence) to 62.5% (security-only) to 5.0% (DeployHardened). At the same time all 12 benign creative controls are admitted at every level (0/12 over-blocked), including dual-use MR authoring, so creative freedom is preserved. In short: a layered, fail-closed static-admission backend statically rejects 95.0% of five classes of XR privacy and manipulation payloads in a live speak-to-code VR system while preserving creative freedom, evaluated automatically and locally, with a measured sub-millisecond per-command validation cost. What it does not do — demonstrate runtime prevention, close the 2/40 lexically-indistinguishable residual, or validate against an independent holdout — we state plainly as the work that must come next.
